# 基于 Modus 源码写文章与分享

目标：写出读者能理解、维护者能复核的文章。先锁定受众与核心问题，再选机制和案例，不把目录或术语清单当成文章。

## 建立事实底稿

核对当前版本和源码漂移，先读 [全局概览](global-overview.md)、[源码依据与版本核对](sources.md)，再读涉及的模块。关键结论在底稿保留“主张、版本、源码/测试位置、证据类型、可公开表达”；不要求底稿全部进入成文。

| 主张类型 | 足够的证据 | 合适表达 |
| --- | --- | --- |
| 当前能力 | 注册、方法体、当前配置、对应测试 | “当前分支提供……” |
| 架构设计 | 设计文档与实现的所有权/失败边界 | “设计将……分开，当前实现通过……维护” |
| 用户需求或目标 | 公开需求、设计提案或用户明确提供的材料 | “希望/设计目标是……” |
| 推断 | 证据链及未覆盖条件 | 明确说“从这些实现可推断” |
| 历史、试点或效果 | 日期、项目、任务、模型、样本、基线与原始结果 | 带适用范围；无材料不编数字或推广规模 |

对外源码引用使用可访问的仓库链接，并指向对应版本。个人路径、未公开材料和会话工作记录不进入成文；发布沿用用户授权。

## 叙事主线

从“事实分散，助手容易缺少业务边界、约束与验证上下文”引出 Modus：机器分析提供可重建证据；助手沿场景完成范围判断与正文；长期知识按系统、领域、模块组织；日常任务渐进读知识并回到当前源码；变化只更新真正受影响的知识。

把价值连接到实现：每种内容有自己的来源、所有者和生命周期；有界上下文交付精确证据、遗漏与继续调查目标；知识维护依赖原位语义修订和并发保护。

| 文章重点 | 推荐机制与源码依据 |
| --- | --- |
| 架构全貌 | `ARCHITECTURE.md`、`paths.py`、`surface.py`；三生命周期与 N/K 交接 |
| 机器如何帮助理解代码 | N1 冻结 → N2 观察 → N3 解析 → N4 入口到效果 → N5 建议 → N6 有界交付 |
| 为什么不能靠聚类直接划领域 | `capability/composer.py`、`projection/proposals.py`、`scope_candidates.py`、Scope 建模模板 |
| 知识如何可维护 | `knowledge_write_session.py`、`knowledge_update.py`、原位修订模板 |
| 检索和上下文开销 | Markdown 索引、BM25 与结构排名、渐进选择、共享预算；不由此推导成本下降比例 |
| 多平台与多仓 | PlatformLayout、常驻指引、宿主调用权限与 workspace 成员隔离 |
| 工程可信度 | 严格协议、摘要、漂移检查、CAS、失败保留、wheel 独立验收 |

维护者材料先讲可观察问题，再给边界、输入输出、失败与修改验证入口。技术文章用真实场景贯穿，再解释关键机制。管理汇报结论先说，用大白话说明当前能力、实际问题、证据和下一阶段；效果数字只来自材料。

图中每条边有调用、装配、协议、配置、数据或材料依据。总览、时序、状态、对象关系各选合适表达；图能渲染不证明边正确。

## 常见事实错误

| 不应直接写的结论 | 当前准确边界 |
| --- | --- |
| 全自动生成完整业务知识 | 分析交付证据，助手调查、确认范围、创作和回读 |
| 图谱完整所以运行链路完整 | 有候选、解析缺口、预算截断与代表路径 |
| 所有发现语言都有精确编译语义 | 发现、通用文本、结构解析、编译语义层级不同；五个 compiler provider 也受工具链限制 |
| verify clean 表示知识准确优质 | 检查客观完整性/发布承诺，语义与表达由作者评审 |
| sync 命令自动写知识 | 命令返回只读候选，助手判断后最小修订 |
| 知识批次全有或全无 | 逐文件 CAS 可部分成功；安装/更新另有事务 |
| 自动载入整个知识库 | 常驻说明提供技能入口，按任务再取证 |
| 所有平台和 Python 版本已验证 | CI 矩阵不等于本次实际运行或远端 CI 通过 |

收稿核对版本、命令、路径、图中的边、完成/失败语义与数字。生成项目知识关于“正文不放源码坐标”的规则只适用于其产品；本开发技能和技术文章不机械套用那套布局。
