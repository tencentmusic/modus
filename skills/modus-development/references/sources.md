# 源码依据与版本核对

开发、评审和技术写作以当前 checkout 为准。贡献者应能仅凭仓库中的源码、测试和公开文档复核结论，不依赖某次开发会话或无法访问的外部材料。

## 按问题选择依据

| 要回答的问题 | 主定义 | 核对方式 |
| --- | --- | --- |
| 当前包与依赖是什么 | [包元数据](../../../pyproject.toml)、[锁文件](../../../uv.lock)、[源码版本](../../../src/modus/__init__.py) | 区分分发名 `openmodus` 与命令名 `modus`，使用当前 checkout 的 CLI |

| 模块如何协作 | [架构设计](../../../ARCHITECTURE.md)、[生命周期边界](../../../docs/knowledge-lifecycle-boundary.md) | 沿入口核对数据所有者、依赖方向、完成与失败语义 |

实现细节以当前注册、方法体、配置与测试共同核对。设计文档解释职责和取舍；需求描述尚待实现的目标。材料与实现不一致时说明差异，不把目标写成已有能力。

## 使用源码基线

`source-baseline.json` 为只读诊断脚本提供文件哈希和模块指南映射，用于定位需要回读的源码。它是比较基线，不是当前版本声明或验收结果。脚本发现变化后，读取对应实现与测试；无需为了匹配基线切换分支或覆盖工作区。

包版本、HEAD 和本地修改从当前仓库读取；不要在指南中复制一份会持续过期的环境快照。脚本不联网，其上游状态不能证明远端最新状态。

## 文档与验证证据

长期文档记录可操作的安装步骤、稳定契约、设计理由和可复现验证方法。具体版本的测试结果、性能数据和兼容性证据随对应 PR、CI 或 Release 保存，并注明源码版本和实际覆盖范围。

对外技术文章引用可访问的源码和公开资料。无法公开的材料不能成为读者复核实现的必要前提；效果数字需要明确样本、任务、模型和对照条件，缺少证据时不写成效果承诺。
