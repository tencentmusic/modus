# Skill 编写与维护

Modus 的 Skill 是可审阅、随包发布的工作流源码。好的指令让助手在真实任务中选对入口、取得必要证据、完成授权范围内的工作，并准确处理失败。本文规定如何维护这些指令；代码设计、文档语言和贡献流程沿用 [贡献指南](../CONTRIBUTING.md)。

## 先确定修改的产品

| 内容 | 主定义 | 读者与职责 |
| --- | --- | --- |
| Modus 自身的开发方法 | [开发 Skill](../skills/modus-development/SKILL.md)、贡献指南、模块 README | 帮助贡献者定位实现、理解取舍、验证修改 |
| 安装后的工作流 | [模板目录](../src/modus/scaffold/templates/README.md) | 指导用户项目中的助手；分发后独立可用 |
| 生成知识的产品设计 | [知识创作契约](authoring-contract.md)及对应运行参考 | 解释证据、正文、所有权和发布边界 |
| 最终项目知识 | 工作流生成的 `modus/knowledge/` | 帮助项目读者理解业务、开发和排障 |

开发规范不自动成为下游项目的团队规范。维护者指南可以引用仓库源码；随包工作流的本地依赖必须在模板分发树中闭合，不能要求读取仅存在于本仓库的 `docs/`、测试或个人环境。

## 选择职责与文件

新增内容前，沿入口找到已有规则所有者和实际消费者，再决定原位修改还是拆分。

| 位置 | 应承载的内容 | 拆分依据 |
| --- | --- | --- |
| `SKILL.md` | 能力、触发条件、关键不变量、工作流选择与细则入口 | 用户可辨识的独立任务；新增公开入口还需更新 `modus.surface` |
| `references/` | 按阶段、产物或条件读取的方法与契约 | 具有独立读取时机、决策职责或维护原因 |
| `scripts/` | 重复执行且需要确定性的操作 | 可验证的输入、输出、依赖和失败行为 |
| `assets/` | 实际进入产出的资源 | 确有消费者，且当前分发机制支持其格式 |
| 开发文档与测试夹具 | 设计理由、维护方法、完整教学样稿和验收材料 | 服务贡献者，不增加普通用户任务的上下文负担 |

短而完整的 Skill 可以只有入口文件。共享规则放在现有所有者处，调用者保留必要摘要和精确链接；只有多个消费者共享同一语义时才提取。文件数量、篇幅或目录对称不构成拆分理由。

Modus 的 init/reinit 共享 K1～K6 创作路线，update/sync 共享增量维护，日常使用按 C1～C6 消费知识。维持这些既有边界，具体路线由 [模板主定义](../src/modus/scaffold/templates/README.md) 导航。跨 Skill 引用是显式的分发依赖，移动文件时一起检查消费者及安装后的路径。

## 写出可执行的指令

`name` 使用稳定、明确的能力名称并与目录一致。`description` 简洁说明能力与触发条件；相邻工作流容易混淆时补充边界。详细步骤放在正文，不能依赖 description 代替执行协议。

正文围绕实际决策组织，回答适用的问题：

- **进入条件：** 哪类请求或已发生的变化需要此流程；续作从何处恢复。
- **输入与依据：** 需要哪些当前材料，哪些内容只是候选，缺口会影响什么决定。
- **动作与权限：** 读写对象、职责所有者、副作用及授权范围。
- **分支与失败：** 可选工具不可用、无匹配、部分成功、冲突和未知写入各如何继续。
- **出口：** 什么可观察结果代表完成，哪些缺口必须保留，何时回到前序步骤。

这些是审查问题，不是每份文件必须复制的标题。复杂阶段可以用输入、动作、出口组织；薄入口直接说明选择条件与委托目标。

规则强度沿用 [创作契约](authoring-contract.md)：必须/不得保护正确性、协议和所有权；应当表达有依据可调整的默认；可以表达可选增强。每条规则尽量写成“在什么条件下，对什么对象做什么，以什么结果结束”。

例如，写“写入返回冲突时，保留已成功的文件，重读冲突目标并重新判断修改；仍有冲突则报告具体目标”，比“确保写入安全”更能指导动作。恢复细节仍由发布合同维护，调用入口只链接，不复制一套重试策略。

语句使用稳定术语和具体动词。解释非显然的原因与取舍，删去重复提醒和无法验收的修饰。HTML 注释也会进入 Agent 上下文，仅用于确有必要的维护信息；执行要求应出现在可见正文中。

## 控制读取成本

每个引用都应让读者知道何时需要它。入口直接链接关键决策所需的细则；按任务选择语言、平台或产物参考。目录层级可表达职责，但避免为了找到一个动作反复穿过只有转发作用的索引。

完整条件和例外应与其约束的动作放在一起。常用路径能够独立完成，特殊分支有明确入口；已经读取且仍有效的材料可复用。上下文丢失后的恢复规则由现有工作流维护。

示例用于说明真实难点，如部分成功、异步完成和规则优先级。区分示例数据与项目事实；命令使用真实接口，可替换参数明确标注。完整教学样稿和参考答案留在测试夹具，避免在评测输入中泄露答案。

## 修改与验证

先写清本次改变的行为或阅读问题，再修改主定义及受影响入口。语义重构需保留原有条件、例外、权限、失败处理和完成口径；如确需改变，按产品行为变化说明兼容性与影响。

| 变化 | 验证重点 | 既有入口 |
| --- | --- | --- |
| 名称、frontmatter、路径、链接、命令示例 | 可解析、可定位、引用可从公开入口到达、与真实 CLI 对应 | `tests/test_scaffold.py`、`tests/test_documented_cli.py` |
| 模板或支持文件增删、移动 | 首次安装、升级、用户编辑保护、卸载、分发完整性 | `tests/test_platforms.py`、`tests/test_project_lifecycle.py`、`tests/test_release_smoke.py`、`scripts/wheel-smoke.sh` |
| 触发、分支、恢复、写入或完成条件 | 代表性任务下的实际选择、动作、副作用和结果 | 对应工作流场景、相关代码测试及人工回读 |
| 生成知识的语义或表达策略 | 当前源码事实与读者任务，必要的实际渲染 | `tests/fixtures/authoring/`、工作流要求的真实项目验收 |

涉及语义变化时，预先列出能暴露该变化错误的场景：应触发与不应触发、正常完成、相关失败或恢复。记录实际输入、版本、观察结果和未验证项。验证强度随风险确定；低风险编辑复用已有检查，避免为句式或标题编写脆弱断言。

模型行为评测与确定性测试分别报告。隔离会话、固定任务与环境、控制参考答案可见性的方法可复用 [知识使用评测方案](knowledge-consumption-evaluation-plan.md)。独立 Agent 验证需要当前任务已授权委派；同一作者回读不能称为独立测试。未执行模型评测时明确说明，不能用链接通过、篇幅缩短或规则数量证明行为改善。

评审关注：新读者能否选对入口，关键条件是否可找到，修改是否落在唯一所有者，失败是否有下一动作，证据能否支持完成声明。具体运行结果随 PR 或 CI 保存，长期指南只维护契约与方法。

## 设计依据

- [Agent Skills 规范](https://agentskills.io/specification)：元数据、资源结构与渐进加载。
- [Anthropic Skill 编写指南](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)：按任务组织、具体示例与真实场景验证。
- [Superpowers 的 Skill 编写方法](https://github.com/obra/superpowers/blob/main/skills/writing-skills/SKILL.md)：用可观察行为检验指令效果。

这些资料解释方法来源；Modus 的实际合同由本仓库维护。外部资料更新不自动改变本项目的工作流或授权。
