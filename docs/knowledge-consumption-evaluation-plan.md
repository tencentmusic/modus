# 知识使用增强评测方案

本文评估 `using-modus` 如何将 `modus/knowledge/domain` 与 `modus/knowledge/constraint` 用于当前任务，重点是编码，以及确有项目知识价值的非代码任务。目标是判断知识是否帮助形成正确决定、完成产出和验证关键边界，同时控制读取与执行成本。

本文于 2026-11-03 整理，是供后续独立使用的方案，不是评测结果。本轮不执行模型评测、不新增评测工具，也不将本方案设为日常任务的固定流程。源码机制的参考版本为 `760c03f5`；C1～C6 是已确认的消费职责划分，不代表该版本已经按六阶段实现。

## 1. 先区分要验证的两个问题

| 问题 | 对照方式 | 能回答什么 |
| --- | --- | --- |
| 消费协议的调整有没有帮助 | 同一份知识、同一任务、同一取证方式，对比现有协议与调整后的协议 | 阶段组织和规则应用是否改善任务结果，是否增加不必要步骤 |
| 两类知识如何互补 | 固定消费协议，对比无项目知识、仅 domain、仅 constraint、两者联合 | 哪些任务依赖业务事实、哪些依赖工程要求、联合使用是否减少遗漏 |

建议先做第一项，再按需要做第二项。不要同时更换模型、知识正文、CLI 检索器和 Skill 协议，然后将全部变化归因于某一个因素。

直接读取文件与 CLI 检索是两种取证方式，Skill 协议统领两者。首轮若只调整 Skill，就以直接读取为主验证；后续若调整 CLI，再增加对应的公开入口用例和效果对照。CLI 并非评测知识使用效果的前提。

## 2. 任务样本

先选择少量有明确答案或行为判据的任务，覆盖下列场景；同一个任务可以检验多个阶段，不必为每个阶段建立独立执行流程。

| 场景 | 重点阶段 | domain 的作用 | constraint 的作用 | 观察结果 |
| --- | --- | --- | --- | --- |
| 修改公开接口中的字段 | C1～C5 | 识别输入、身份、兼容和实际消费者 | 确定校验、映射、复用入口及版本限制 | 字段语义一致，相关消费者与错误路径得到检查 |
| 修改恢复次数或失败处理 | C3～C5 | 区分可改变的旧规则与仍需保持的完成口径、副作用边界 | 选择合适的执行入口、重试和资源处理方式 | 不重做已经生效的结果，不把所有失败都视为可重试 |
| 批量处理使用共享执行能力 | C2～C5 | 明确顺序、部分成功和失败对业务结果的影响 | 提供并发上限、共享资源所有权与准确 API | 不关闭借用资源，不虚构 API，行为满足任务要求 |
| 场景入口与规范专题使用不同词汇 | C2、C3 | 提供业务场景和关联线索 | 通过导航链接提供适用专题 | 能沿链接取得关键要求，不能只靠原始查询词命中 |
| 规范示例的前提与例外分在不同小节 | C3、C4 | 判断示例是否满足当前业务需要 | 限定平台、版本、适用范围和例外 | 不脱离条件复制示例，截断时继续读取必要范围 |
| 知识正文与源码或明确规范不一致 | C3、C4 | 提供待核实的现状描述 | 提供期望要求及其来源 | 区分现状与要求；既不照抄旧事实，也不因代码偏差废弃规范 |
| 已知路径的小范围调整 | C1～C5 | 已有证据够用时直接复用 | 只处理与本次变化相关的要求 | 不全库扫描、不重复获取相同证据、不强制输出阶段报告 |
| 业务解释、使用说明或故障分析 | C1～C5 | 支撑概念、因果、条件、状态和恢复解释 | 仅在涉及工程选择或实现边界时参与 | 结论有依据；声称当前实现行为时核验源码；普通说明不加载无关编码规范 |
| 仅整理用户给定材料，且无需项目事实 | C1 | 无需参与 | 无需参与 | 不激活项目知识检索和知识同步 |
| 实现变化后的知识影响，以及只读任务的收尾 | C6 | 找到受影响主定义、案例与关联 | 保护人工规范，识别实现偏差 | 按实际修改最小维护；无影响静默结束；只读任务不自动写回 |

可用现有夹具校准任务与检查方式，但这些材料已参与当前设计，不应冒充未见过的独立验证集。正式效果评测应另留未用于调优的任务变体，并由熟悉项目事实的维护者核对预期结果。

## 3. 比较条件

比较时固定源码基线、任务描述、模型及配置、可用工具、环境和总执行预算。每次运行使用独立会话与独立工作副本，不继承其他组的答案、修改或对话摘要。若宿主存在跨会话记忆，也应控制或记录其影响。

四组知识对照都保留完成任务必需的源码、用户需求及共同工程指令。分组只控制项目知识正文的可见范围：无项目知识、domain、constraint、domain 与 constraint。共同指令中若已经包含业务或工程要求，应记录这些重叠信息，不宣称它们完全由知识库提供。

概览、导航和交叉引用也可能泄露被排除的知识。可提供相同的中性定位入口，但不要让仅 domain 组通过链接读取 constraint 正文，反之亦然。记录两类知识实际存在的内容重叠，不为获得漂亮对照而改写其原始性质。

不给被测助手提供参考答案、现成 solution、隐藏检查或其他组结果。若采用现有夹具，需要将任务输入和评审材料分开。评审者尽量在不知道分组的情况下先判断产出，再查看过程解释失败原因。

## 4. 判断结果，而不是统计引用数量

| 维度 | 判据 | 不能作为替代的指标 |
| --- | --- | --- |
| 业务正确性 | 满足需求，保持未授权改变的业务边界，正确处理失败与恢复 | 读了多少 domain 文件、答案中出现多少业务词 |
| 规范适用性 | 选对规则性质、适用路径、平台和版本，正确处理例外 | 引用了多少条规范、是否复述全部规则 |
| 实现与复用 | 使用真实且适用的能力，控制副作用与资源所有权 | 与规范示例的文字或代码相似度 |
| 验证有效性 | 检查能够暴露本次关键错误，结果可复核 | 测试数量、仅编译通过、与实现同构的断言 |
| 非代码产出质量 | 回答目标问题，事实与推断分开，必要边界清楚 | 篇幅、术语密度、固定表格是否完整 |
| 知识维护边界 | 维护实际受影响事实，保护人工内容，只读任务不写回 | 机械 sync 返回 noop、知识核验 clean |
| 使用成本 | 完成任务的总时间、实际 token、工具调用、读取范围与重复读取 | 仅 CLI 单次耗时、仅最终答案长度 |

对每个任务预先列出必须满足的行为及适用规范。将结果记录为满足、部分满足、不满足或不适用，并保留支持判断的代码、输出或文档位置。关键失败单独报告，不用平均分掩盖，例如重复业务副作用、违反明确要求、错误平台实现、虚构 API 或未获授权的知识写入。

性能成本按完整任务记录；CLI 的单次预算不等于宿主多轮取证的总成本。没有可靠 token 或时间数据时标记未采集，不用估算值冒充实测。

## 5. 沿 C1～C6 归因

| 阶段 | 失败时优先检查 |
| --- | --- |
| C1 任务定界 | 是否误激活、漏掉变更用途，或未识别影响实现的知识需求 |
| C2 联合定位 | 是否找到相关主定义与规范入口；已有链接是否被忽略 |
| C3 证据收敛 | 是否漏掉前提、例外、失败路径或关键源码；是否重复取证而不解决缺口 |
| C4 产出决策 | 是否混淆旧行为与新要求、事实与规范、通用建议与硬约束 |
| C5 执行与验收 | 决定是否落实到实际产出；检查是否能发现关键偏差 |
| C6 知识留存判断 | 是否遗漏实际影响、扩大维护范围，或把只读发现直接写回 |

只依据可观察证据归因，包括实际读取、工具结果、方案说明、差异、验证与最终交付，不要求助手暴露内部思考。无法确定失败阶段时保留未知，不从一份错误答案反推完整过程。

## 6. 后续执行建议

先用小样本验证任务描述与判据是否清楚，再安排独立任务比较。执行次数与成本由后续评测负责人决定；若条件允许，每个任务和分组重复运行，以观察模型波动。单次成功不能证明普遍有效。

按场景分别报告收益和代价。联合知识未必在每个任务上都优于单类知识：普通业务解释可能只需要 domain，小范围调整也可能已有足够上下文。只有知识实际改变了正确决定、减少了关键遗漏或降低了完成任务成本，才计为有效增强。

不要预先承诺收益比例或设定没有基线依据的统一耗时阈值。没有可重复收益的增强应缩小触发范围或继续修正，而不是直接增加读取量和固定流程。

建议每次保留以下记录；这些记录属于离线评测，不进入普通 using-modus 任务。

| 任务 ID | 源码与知识版本 | 协议版本 | 分组／取证方式 | 模型与配置 | 行为结果 | 适用规范结果 | 关键失败及证据 | 成本 | 归因阶段 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 待执行 | 待记录 | 待记录 | 待记录 | 待记录 | 未评测 | 未评测 | 未评测 | 未采集 | 未判断 |
