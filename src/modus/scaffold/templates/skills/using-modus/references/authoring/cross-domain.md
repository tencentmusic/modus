# 跨域事实与交接

本合同同时用于串行与已授权的并行创作。各域正文不重叠，不代表业务事实互不依赖；关联信息必须在 K1/K2 建立，K3/K4 持续核对，K6 最终组装。根作者负责共享事实的裁决与传播，不能只在最后拼接各域摘要。

## 在唯一执行卡保存共享基线

在原卡的主定义/场景记录中，保存一份“已接受的跨域协作基线”及可辨认的修订标识；这是正文记录，不增加机器 schema 字段或回执文件。每条交接包含：

- 业务场景、发起方与承接方、双方 Domain/Module 稳定 ID；
- 事实主定义的所有者和实际路径/章节；未成稿时保留预定落点与可定位证据，不把计划链接当成事实；
- 公开契约、输入输出与字段/状态映射、采用的术语；
- 同步/异步方式、交接前已提交事实、下一完成信号、失败残留、重试/恢复责任；
- 双方源码/配置/明确材料依据、已核验范围与未决冲突；
- 使用此事实的目标页、图与案例，以及需要重新核对的范围。

机器取证按[消费路线](evidence/machine-packet.md#六阶段消费与可恢复记录)定向读取 service-boundary 与 serviceRelation（包含入边/出边），保留 recordId、见证、精度和未解析侧；缺少机器关系不证明没有依赖，仍以双方源码/配置补证。K6 用这些关系反查交接清单和最终正文，不能只检查清单上已经出现的关系。

只记录影响交接的事实，不复制整份对象字典或正文。对同一术语的不同含义标明作用域；当前实现与业务要求冲突时并列记录，不能把业务目标伪装成已实现。仅有一侧证据时说明另一侧无法证明的保证，不凭名称补完。

## 依赖决定顺序

先在 K2 为所有域安排主定义与依赖，再展开当前域。消费者写作前实际读取已接受的交接和相关主定义；提供方未成稿时按其当前证据核验，不仅接受任务消息中的总结。

- 独立域可以串行，获得授权后也可以并行。
- 有单向依赖时先稳定提供方契约，再写消费者的依赖段落；无关场景仍可推进。
- 循环依赖先由根作者联合读取双方入口、对象、状态与完成信号，形成最小共享边界，再分别成稿；不因循环而擅自合并业务身份。
- 归属或完成/恢复责任未决时暂停受影响结论，继续不依赖它的工作；不能填默认保证以维持调度。

## 变化传播与双向核验

域作者发现新的跨域关系或冲突时，返回具体证据、受影响主定义与消费者，不直接改其他域。根作者回读双方事实后原位修订共享基线，标明变化与受影响页，并通知正在工作的作者重新读取；串行切域也必须读取这份最新基线。

worker handoff 必须回报实际使用的协作基线标识。根作者验收时与当前基线比较；有变化就核对相关页，不能以旧基线下的 reviewed/clean 直接接受新结果。已验收事实受到影响时按[发布合同](publication.md#逐篇验收与事实对账)重开受影响 Domain/Module 和页面，更新正文、图、案例及验收记录，其他域不重写。

K4 检查本域每个交接是否与对方事实相符。K6 逐条从提供方主定义走到消费者场景，再从消费者的输入、返回与恢复描述反查提供方；核对最终文件，不能用双方都写“调用成功”判定一致。无法消解的冲突保留来源、影响与下一动作，不能隐藏在根概览里。
