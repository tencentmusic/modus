# 根概览合同

- **读者任务**：让首次读者理解项目价值、运行方式、能力地图和维护入口。
- **结构**：稳定路径 `architecture-overview.md`；按项目自然组织项目总览、运行架构、能力关系、知识导航、开发/验证/排障入口。
- **证据**：只引用构建/部署/运行单元和下层知识，不保存方法、符号与行号清单。
- **适配**：Surface 改变强调点，语言只改变术语；不改变根概览的系统级视角。

根概览必须回答：项目服务谁、解决什么、不负责什么；入口怎样到达能力域；权威与派生数据如何分层；Domain 之间为何交接、谁拥有状态、何时才算最终完成；贡献者从哪里构建、验证与排障。

根概览在 K6 创作，输入是 K4 最终领域/模块和 K5 已创作或保留的项目规范。先核对这些文件的实际版本与跨域交接，再建立系统叙事；不能在领域尚未闭合时用概览猜测结论。已存在的概览在 reinit 中按真实影响修订。

## 推荐展开节奏

标题后可提供页内导航，并按当前项目事实自然覆盖以下内容：

1. **系统目标与角色**：主要使用者、触发场景、业务/工程结果、明确非职责和外部前提。
2. **能力地图**：全部正式 Domain 及其关键 Module；表格说明进入条件、权威结果和边界，不能只列名称。
3. **运行架构与分层**：构建模块、部署/运行单元、入口、编排、数据访问、异步执行和共享资源的真实关系。
4. **Domain 关系**：谁调用谁、传递什么、谁拥有数据、同步返回是否代表最终完成、失败责任停在哪里。
5. **关键端到端链路**：选择真正贯穿多个边界的代表任务，说明触发、主要步骤、权威写入、完成信号与恢复入口。
6. **开发与排障导航**：把真实问题路由到 Domain、Module、专题、测试和命令，而不是罗列目录。
   同时提供已有 global/team 规范入口；必要约束摘要保留适用范围与规则链接，详细依据、例外和验证留在规范主定义。待确认要求不能表述为当前系统保证。
7. **证据范围与缺口**：源码 revision、使用的材料、已验证范围，以及确实无法从当前仓库证明的外部事实。

## 图表与工程表达

存在多个运行单元或真实跨域交接时，使用一张系统级主图配合职责/交接表。图优先表达运行时参与者、调用/事件方向、权威状态和最终完成，而不是复刻目录树；表格补充下列精确信息：

| 关系 | 应说明 |
| --- | --- |
| 运行单元 | 入口、责任、进程/部署边界和启动方式 |
| Domain 交接 | 业务目的、输入输出、状态所有者和完成信号 |
| 数据分层 | 权威事实、派生投影、缓存/索引和刷新责任 |
| 失败定位 | 首个可观察症状、责任边界、恢复入口和验证方式 |

多 Domain 项目的系统图不能用一张“Domain 名称列表表格”代替；表格负责精确对照，Mermaid 负责呈现方向、层次或时序。不得把源码 package 画成业务 Domain，把构建依赖画成运行调用，或从同仓推断同进程/已部署。

## 深度判断

根概览不是所有下层文档的摘要拼接。它应让首次读者在不打开源码时形成正确的系统心智模型，同时把字段、分支和恢复细节链接到唯一主定义。若内容只说明“项目采用某语言和若干模块”，没有角色、权威责任、跨域完成语义和故障导航，仍是未完成概览。

完成标准：新读者可以复述系统主线，维护者能找到能力所有者、知识入口和验证入口；具体字段、分支和恢复下沉到 Domain、专题或 Module。
