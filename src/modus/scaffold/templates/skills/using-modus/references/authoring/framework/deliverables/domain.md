# 领域契约

- **读者任务**：解释一个长期能力边界，并把读者路由到专题和 Module。
- **结构**：稳定路径 `domain/<domain>/SKILL.md`；自然覆盖领域定位、结果与边界、专题导航和 Module 全景。
- **证据**：调查可以使用源码，正文不展示方法级路径、符号和行号。
- **适配**：跨多个 Surface 时合并业务关注点，不把技术形态变成新的 Domain。

Domain 必须回答服务对象、输入、业务结果、权威责任、修改权、完成信号、相邻 Domain 的接管点和明确非职责。专题导航说明每个入口回答什么；Module 导航说明何时进入、产生什么结果、故障或修改从哪里继续。

## 推荐内容结构

Domain 入口保持导航层视角，可按项目语言自然组织，但应形成以下阅读路径：

- **定位、结果与边界**：用直接结论说明服务对象、触发、输入、权威结果、最终完成和非职责；边界表应解释“为什么属于/不属于本域”。
- **业务流与相邻域交接**：从触发者到本域结果，再到已验证的跨域接管点；说明状态和数据所有者，不能只画调用箭头。
- **专题路由**：对六专题和 Business 入口逐项说明“何时加载、能回答什么本域问题”，避免统一写成“查看详情”。
- **Module 全景**：目标语言能力名、职责、主要任务、进入条件、结果、故障/修改入口和链接；源码符号留在专题或 Module。

推荐使用两张高信息密度表：

| 维度 | 直接结论 | 边界说明 |
| --- | --- | --- |
| 服务对象/触发 | 当前项目事实 | 谁不会从本域获得结果 |
| 权威结果 | 本域创建或维护的事实 | 派生视图和外部事实归谁 |
| 完成信号 | 何时对调用者/用户真正可见 | 受理、异步完成与最终一致的区别 |
| 相邻交接 | 上下游 Domain 与目的 | 交接前后各自责任 |

| Module | 主要任务 | 结果与进入条件 | 修改或排障入口 |
| --- | --- | --- | --- |
| 目标语言能力名 | 真实角色动作 | 可观察结果 | 精确链接到手册/专题 |

三个以上参与方、跨 Domain 交接或所有权容易混淆时使用上下文/边界关系图，并配合责任边界表。模块彼此独立时只用表格，不为形式完整画图。模块导航表只是索引，不算对状态、协作或对象关系的解释性图。图中表达能力、方向、责任和完成，不表达源码依赖。

如果 Domain 入口只是“一段领域介绍＋六个专题链接＋模块名称表”，没有权威结果、完成口径、相邻域接管和真实任务路由，它仍是空壳导航。

完成标准：读者能判断一个需求是否属于本域，能选择正确专题或 Module，并且相邻域不会同时宣称拥有同一事实。
