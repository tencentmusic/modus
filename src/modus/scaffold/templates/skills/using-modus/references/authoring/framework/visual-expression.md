# 图、表与正文

图用于显著降低关系理解成本，不是装饰、覆盖证明或数量门槛。表格表达精确映射，正文解释原因、边界、完成、例外和恢复；即使 Mermaid 不渲染，表格与正文也应足以理解。

先区分两类视觉内容：

- **导航型**：目录树、专题链接、Module 清单和名称对照表，帮助读者找到页面；
- **解释型**：架构、上下文、时序、状态、决策、对象关系、数据流和资源生命周期，帮助读者理解方向、责任或变化。

导航型表格有价值，但不能兑现已经由复杂度触发的解释型图表需求。一个 Domain 已有 Module 导航表，不等于它的异步状态、跨域交接或对象关系已经被解释。

## 触发与选择

逐 Module、逐核心场景评估选图，而不是只在 Domain 层面评估一次。出现多参与方顺序、同步/异步交接、持久状态与恢复、多条件分支、跨 Domain/进程/资源、权威与派生状态区分，或仅凭线性文字容易误解责任与完成时点时，必须给出对应的解释型表达。已发现真实复杂机制时，不能仅以“文字足够”“已有导航表”或“本域已有图”为由豁免。

| 问题 | 首选表达 | 必须配套 |
| --- | --- | --- |
| 分层、所有权或资源关系 | 架构/关系图 | 职责与所有权表 |
| 多参与方推进顺序 | 时序图 | 完成、失败、超时与责任说明 |
| 条件改变结果 | 决策表；顺序重要时流程图 | 条件、结果、短路与例外 |
| 持久状态迁移 | `stateDiagram-v2` | 转换表与恢复说明 |
| 对象、基数与表示映射 | ER/对象关系图 | 字段、事实源和写入责任 |
| 数据血缘或资源生命周期 | 数据流/依赖/生命周期图 | 检查点、配置、回滚与销毁边界 |

顺序、交接、并发、回调、返回后继续执行等时间关系用时序图；任务的条件路径和副作用顺序用流程图。平铺字段或条件比较可用表格，表格不能代替复杂时序。模块中的导入、迁移、批量处理等场景若实际涉及任务、线程池、远端调用或部分成功，应在该场景紧邻正文画出主线、受理/完成分界和关键失败路径；不能只链接状态专题。没有这些机制时不得从模块名称推断它们存在。

图的取舍必须能解释具体阅读收益：读者会在哪个交接点误判、图展示哪些关系、哪些精确条件交给表格。简单关系可以不用图；已有主图确实回答同一个问题时，可以就地解释当前场景并精确引用。不同问题分别规划，先画最容易误解的机制，再决定是否拆图；不以覆盖每页、填满篇幅为目标。

简单同步调用、单条件规则、无副作用纯函数或短列表通常不画图；用户明确指定的产物最低配图要求优先。init/reinit 将这些要求写入现有执行卡正文，并用已有 visual 项逐一规划目标与读者问题，不新增质量配置或图数评分。撤销某个候选图不能自动豁免用户要求；确无证据形成所需图时报告具体缺口。不得把目录树、候选图谱或类依赖直接当业务架构。

图形从读者问题反推，不从“需要一张 Mermaid”反推内容：

- 根概览回答系统怎样分层、Domain 与运行单元怎样交接；
- Domain 回答本域与角色、相邻域、权威事实的边界；
- Module 回答一次任务经过哪些参与者、判定、写入和完成点；
- API 回答分流或返回后仍继续的调用链；
- State Machine 回答持久状态怎样合法迁移；
- Downstream 回答责任何时从一方转到另一方；
- Object/Infrastructure 回答关系、映射、依赖和生命周期。

同一页面可以因多个独立问题需要不同表达，例如状态图说明“可以怎样迁移”，时序图说明“谁在何时推进”。不要为了追求一页一图把两类信息塞进难以阅读的巨图，也不要用一个导航表豁免所有解释型图。

## 证据与唯一主图

图中每条边必须由实际调用、注册装配、协议/IDL、配置、SQL 读写、消息生产消费、测试或明确材料支撑。节点使用业务名称；源码路径和行号只进入目标文档 frontmatter 的 `anchors.locations`，相邻正文用自然语言说明支撑该边的行为和边界。

同一机制只有一份完整图：系统/跨域关系在根概览，Domain 边界在 Domain，单场景主线在 Module，外部交接在 Downstream，持久状态在 State Machine，对象关系在 Object，资源生命周期在 Infrastructure。其他页面只保留当前上下文说明与精确链接。

同一事实可以在不同读者视角中出现：模块图解释一次操作，状态图解释合法迁移，协作图解释责任交接。每张图说明自己的问题和省略范围，并链接完整主定义；允许这种必要的场景投影，不复制整张完整机制图或另起一套状态解释。

init/reinit 执行卡在 Scope 阶段只登记 visual 候选。当前 Domain 的 Module 证据闭合后、开始写六专题和 Module 前，必须依据实际发现重新检查状态、时序、决策、对象和资源关系，形成最终决定；出现新事实时立即增补或撤销，不等全域文件写完。每项决定使用稳定 visual id。实际落地图或表时，在内容前紧邻写入 `<!-- modus:visual:<id> -->`，并把卡片状态从 `planned` 改为 `authored`；证据证明不再需要时改为 `waived` 并写具体原因。发布器按 id、目标和表达类型核对承诺，不用全局数量代替判断。

规划每项 visual 时在执行卡正文写清它要消除的误解、触发它的复杂关系、唯一目标文件和表达类型。不能只登记“module-map/table”就结束评估，也不能因为本域已经有一张图或表就停止。状态图回答“允许怎样迁移”，不能替代“谁在何时推进”的时序图；专题主图也不能自动豁免某个 Module 独有的异步交接或决策机制。每个独立读者问题分别选择最小有用表达。

落图后立即做配套回读：节点和边使用业务名称；方向、同步/异步、状态所有者与完成信号和正文一致；表格覆盖图中无法精确承载的条件与责任；正文说明失败、例外和恢复。图不能独立证明实现，图中的每条边都应能回到相邻文字、表格或源码证据。

## 实际阅读与渲染检查

每张图分别检查三件事，结果不能互相替代：

| 检查 | 必须确认的内容 |
| --- | --- |
| 事实与图文 | 每条边有依据；条件、状态、方向、责任和完成信号与正文一致 |
| 语法与渲染 | 当前阅读环境或已有 Mermaid 预览工具确实能生成图形；无解析失败 |
| 页面阅读 | 正常阅读宽度下标签可辨；没有裁切、节点拥挤、连线标签遮挡或过度缩小 |

图前说明阅读问题，图后解释关键分支和边界。长标签移到邻近文字或表格；复杂图按总览与局部拆开，保持接续点和术语一致。对图的语义修订或重新布局后，重新检查受影响图及相邻文字。参见[拆图样例](examples.md#复杂图的拆分)。

渲染使用当前已有工具与主阅读环境，不要求安装新平台或开发工具。记录实际使用的环境、目标文件及未验证项；预览不可用时继续事实和文字检查，但不能声称视觉验收通过。阅读器变化可能影响排版，Markdown 或 Mermaid 语法有效不能证明所有宿主中的显示效果。

reinit 在参与者、方向、所有权、状态、条件、完成或恢复变化时更新主图；实际裁切、拥挤或渲染错误也可在受影响范围内进行 content-repair。行号和纯措辞变化本身不触发重画，不为新版样稿风格统一重排全部旧图。
