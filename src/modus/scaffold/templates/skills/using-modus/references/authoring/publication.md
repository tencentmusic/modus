# 语义回读、机械核验与安全发布

发布分成三个不能互相替代的层次：Agent 语义回读、确定性机械核验、安全写入。

init/reinit 执行完整的领域与全局验收，并使用原执行卡完成 publication 和清理。update/sync 以[增量维护流程](incremental.md)确定受影响页面及关联上下文，只复用对应的回读、预览、普通 verify 与 CAS 规则，不新建执行卡或执行全量抽查；下述执行卡记录、机器 coverage 和阶段状态仅适用于 init/reinit，增量结构确认与结束结论回到增量流程。

## 语义回读

先在 Domain 内逐篇回读本轮目标正文，再做一次全局回读，并对发现的问题定向返回：

- 新人能否理解系统/Domain 边界并复述一个完整场景；
- 贡献者能否找到主定义、修改点、扩展边界和真实验证入口；
- 维护者能否区分受理与完成，定位失败残留及自动/人工恢复；
- 公开入口、关键字段、规则、状态、资源与协作是否各有唯一主定义；
- 跨域方向、事实所有者、术语和完成信号是否一致；
- [初始化质量要求](framework/index.md#初始化质量要求)规定的案例/图形是否逐篇兑现，额外图是否有用、逐边有据且没有重复主图。

### 通用可读性问题

按[术语解释、行为表达与来源追溯](framework/localization.md#术语解释行为表达与来源追溯)回读，不依赖特定业务缩写、运行形态或正文语言：

- 目标读者能否理解谁在什么条件下做什么、得到什么结果？
- 能否区分正常流程、失败、例外和恢复方式？
- 必要的技术标识是否解释清楚，并保留准确拼写；尚未证实的含义和适用范围是否明确？
- 已有明确目标语言定义或枚举映射的术语，是否在业务段落、条件表、案例、图中标签和本轮说明性注释中实际采用，且原始协议值仍保持准确？
- 表述简化后，是否仍保留影响行为的关键条件？

这些问题用于 Domain 成稿、全局发布和局部 update/sync 的受影响正文，不要求在产物中增加固定章节、术语表或检查回执。按[编辑规则](framework/editorial.md)核对段落、步骤、表格、图和案例的分工；按需参考[对照样稿](framework/examples.md)，不把样稿的标题、篇幅或示意事实当作当前项目合同。

Domain 作者必须逐篇完整回读本轮本域全部目标正文，包括六专题及其分片、全部目标 Module 和 Domain 路由。先核对事实、字段、分支与覆盖，再检查行文、图文配合和案例，修复后重读受影响内容。全局阶段检查跨域归属、导航、引用、术语和完成口径，并至少覆盖最薄、最新和最复杂的 Domain，在每个被抽查 Domain 中读取 Domain 路由、六专题以及简单、普通和最复杂的代表性 Module；该抽查只作二次校准，不能替代域内逐篇验收。

回读时隐藏 frontmatter，只根据正文判断开发者能否说明怎样运行、哪里权威写入、何时完成、失败停在哪里以及怎样修改和验证。正文不得出现完整源码路径、`path#L` 或“证据”清单；接口、字段、配置、命令、代码示例及理解行为所需的限定符号保留准确拼写并解释作用。不同 Domain 若明显分成“详实工程手册”和“同长度摘要”两档，且没有事实复杂度理由，不能发布。

出现下列模式时，即使 publication 验证为 `clean`，也要返回对应 Domain 重写，而不是直接发布：

- 大量 Module 是同长度短文、相同三段话或没有真实场景 H3；
- API 只有“调用 Service 后返回”，Object 只有类名，Rule 只有职责介绍；
- 缩写或代号没有可靠定义却被扩写，或同名异义被合并；方法、布尔值和状态只复述标识，成功返回被误写为最终完成，或简化后丢失关键条件与例外；
- State Machine 已出现多个持久状态却没有迁移表或状态图；
- Downstream 只列依赖名，Infrastructure 只列中间件名；
- 图表只有目录树、Module 导航表或名称对照，没有解释真实方向、状态、决策、关系或生命周期；
- frontmatter 源码锚点大多集中在文件首行、类声明或文件列表，无法支撑触发、判定、写入、完成与恢复；
- Team Standard 没有把本项目的命名、结构、模块边界、注释、错误处理、扩展兼容和一致性机制落实为可执行约束。

抽查不是固定篇幅、标题数或图数门禁。它要求作者回到实际事实判断：本页是否让目标读者完成任务，表格是否精确，图是否解释了真实复杂关系，源码证据是否支撑正文结论。

发现边界变化回到 Scope；发现证据缺口回到场景闭合；发现跨域冲突回到相关 Domain。不要用根概览的宽泛描述掩盖下层冲突。

### 逐篇验收与事实对账

把“已完整回读”落实到可定位的页面和结论。init/reinit 在执行卡已有主定义/结果部分，列清本轮目标：六专题及实际分片、全部 Module、Domain 路由；共享产物由根作者同样记录。目标清单来自确认范围与计划，不能只列已经生成的文件。每篇完成后原位简记以下事实，不新建 receipt、评分或 schema 字段：

| 记录 | 要求 |
| --- | --- |
| 目标与读取范围 | 精确文件、接口/对象/场景范围及验收时最终内容的哈希；验收版本不覆盖写入前的 CAS 基线，整篇读完，截断则接续缺失部分 |
| 内容对账 | 接口、字段、规则、状态、协作、配置与场景清单各自落点，关键分支、示例结果和跨页核对结论；本页案例/配图要求的兑现或具体缺口 |
| 编辑与图文 | 实际发现并修正的段落/表格/图问题；无问题时说明检查了什么 |
| 预览与下一动作 | 工具/阅读环境、实际查看章节范围与逐图结论；未验证章节、图、影响及仍需完成的动作 |

不用复制全部正文或工具日志；简单页可以用一条短记录，复杂页按接口或场景分组。路径清单加“全部通过”不足以说明实际验收。未读页、未展开接口/字段、只有目录的复杂场景必须回到原作者补齐；“证据缺失”须有已查范围和具体影响，不能掩盖尚未调查。

K5 的逐条对账还核对规则性质、原始机制、使用者、反例与验证入口，区分首次填充、保留和明确委托维护；K6 核对概览实际消费的 K4/K5 版本、跨域交接与规范摘要。共享产物的验收记录保存在原卡正文，不给它们伪造 Domain/Module 身份或新增状态。下层变动影响概览或规范适用性时，重新核对受影响引用后才能收尾。

按[事实投影](evidence/scenario-closure.md#从机器线索到正文主定义)检查已核验事实是否真的进入读者可见内容。例如已找到锁和消息发送，却只在元数据留了方法锚点，正文仍写“保存成功即完成”，属于事实未消费；六专题都有该方法名也不能通过。再选案例中的实际输入，逐步核对命中条件、字段前后值、返回阶段、最终信号和失败残留，与图和操作步骤相互校验；每个场景的差异应能解释，不能只复述相同流程句式。

每篇依次完成三类工作：

1. **对范围。** 由证据清单找到每个接口详情、字段定义、规则、状态转换、协作交接、资源配置和场景；再由正文反查依据。共享定义必须实际读到对应成员，不能把链接存在当作内容存在。域级 coverage 另行执行，不能替代此项。按[机器消费记录](evidence/machine-packet.md#六阶段消费与可恢复记录)反查相关 evidence/signals/关系的事实主落点，以及未采用、歧义、反证和预算省略的处置；有锚点不代表该事实已写入。
2. **对事实。** 对关键分支分别核对输入条件、选值方向、写入/副作用、返回与最终完成。将 API、Object、Rule、State、Module、图和案例中同一事实并排检查，尤其关注否定词、`0/1`、优先级、fallback 方向、重试资格与部分成功。按本轮目标语言，从已核验的业务名称/枚举映射反查本轮各页的自然叙述和图中标签，确认同一类型/字段含义一致；字典已有目标语言释义而模块仍仅用原码属于待修内容缺陷，不能因映射存在就通过。精确代码、载荷、原始日志不做语言替换；不能靠扫描英文词一律判错。存在冲突时回当前源码裁决，不能多数表述一致就认定正确。
3. **对阅读。** 隐藏元数据连续阅读目标页，按编辑合同修正标题层次、长段落、宽表、空泛列表与跳转依赖；按图文合同核对选型和图前/图后说明，再做实际预览。修订后回查事实并重读受影响内容。

只有逐篇记录覆盖全部本轮目标、逐项对账完成、[跨域交接](cross-domain.md)已与最新共享基线核对、已知事实/内容/排版问题已修复，且原有 evidence/coverage 条件满足时，才能由根作者推进相关 `reviewed`。目标阅读器不可用时可以保留明确的预览限制完成其余语义验收，但不得记作视觉通过；已观察到的渲染失败、裁切或无法阅读需先修复。`reviewed` 和 publication `clean` 都不能清除记录中的视觉待验项，预览未完成时按下述规则保留卡片与续作位置。

后续编辑改变已验收事实、案例或版式时，旧记录不再证明修改后的内容。根作者将受影响且原为 `reviewed` 的 Domain/Module 回到已有 `authored` 状态，标明待复查页；若证据本身失效则先补证，不用 `authored` 掩盖缺口。只重读受影响页及其事实引用处，修复并更新原记录后再恢复 `reviewed`。并行作者通过 handoff 提议状态变更，不直接写卡。

### 独立读者与实际预览

宿主支持且当前授权允许时，可按[执行策略](execution-strategy.md)用隔离上下文的独立读者检查正文能否回答真实任务，不让其依靠作者的未写出推理补齐答案；返回具体缺口与误解位置，由原作者修订。无法使用隔离上下文时，当前作者转换读者视角自查，不能称为已完成独立读者验收。这是现有回读的增强，不改变委派授权、正文所有权或执行状态。

使用可用的目标阅读器或实际预览检查本轮目标页面：Mermaid 能否显示、文字与标签是否可辨、内容是否裁切或溢出、表格是否过宽、复杂图是否需要拆分。逐图按[实际阅读与渲染检查](framework/visual-expression.md#实际阅读与渲染检查)分别核对事实、渲染和页面效果，发现问题后修订并重新查看受影响页面；只读 Markdown、检查 fence 或看到编译成功都不等于布局已验收。

预览不可用时，记录具体页面、工具限制、未验证项与影响，不虚构截图或渲染通过结论。init/reinit 把编辑安排、实际回读与预览结果、待修订问题保存到唯一执行卡已有正文的主定义/图形计划、结果或缺口、下一动作中，不新增 schema、状态、评分或平行 receipt。update/sync 只逐篇回读受影响页面与关联上下文，对变化的图表或版式做预览，不为此建卡、读取初始化 bundle 或检查全库。

### 整页预览范围与未验证项

先确定本轮实际使用的阅读环境与正常宽度，说明它是目标阅读器还是替代预览；不要求验证所有宿主。init/reinit 对本轮新写或实质修订的页面从页首连续查看到页尾，可滚动或分段截图，查看区域须衔接；全页长截图若缩小后无法辨字，仍需分段查看。首屏、随机表格、页面无横向溢出或截图文件存在都不能证明整页已读。已有且未变化的页面可以复用同一版本、同一环境的有效预览记录。

逐页记录查看到的标题范围；未看完就留下具体续看标题。长表须查看起止与中间各组，图须全部实际查看并和前后文字联读，内部导航须检查落点。若页面只有文字，也要检查中后段的标题、段落和列表密度。这里要求完整阅读覆盖，不规定截图数量、字号、像素或统一文件长度。

例如，实际只查看到“新增请求”时，记录“已看页首至新增请求；编辑请求至页尾待看；图 x 已渲染并查看、图 y 尚未渲染”。这是记录方式示例，不能预填为已经执行。正文语义回读、页面完整预览和图形检查分别写结论，避免一句“全部页面已预览”掩盖剩余章节或图。

发现版式问题时修订实际 Markdown，再重看变化部分及其前后衔接；修改影响整页布局时重看整页。临时预览的自定义 CSS、加宽画布或缩小字号只改变检查环境，不能作为正文问题已修复的证据。整页修订后按新版本更新原记录，不沿用旧截图证明新稿。

init/reinit 中工具不可用、只完成部分预览或用户明确将视觉效果留待另行试用时，可以交付已完成的正文并说明范围，但保留唯一执行卡中的待验页面、章节、图和下一动作。能力限制具体记录后继续其他可做工作，不为同一限制反复探测或反复请求批准；恢复时从这些位置继续。update/sync 将受影响范围的未验证项随任务结果说明，不新建卡。结尾分别报告内容完成范围、机械核验、整页预览覆盖和逐图结果，不能把“内容已完成、视觉待验”表述为全部验收完成。

## 机械核验与发布承诺

普通 `modus knowledge verify --json` 只检查机械完整性：Markdown 可读与 fence 闭合、canonical 知识路径、相对链接和锚点、仓库相对源码引用、锚点漂移、本机绝对路径、高置信敏感值、路径/符号链接安全，以及声明过的 Module metadata 能否解析且不与物理身份冲突。需要局部反馈时可以运行 `--domain <slug>`。

init/reinit 终稿在删除执行卡之前运行一次 `modus knowledge verify --publication --json`；工作区从根目录为每个已确认创作成员传入 `--member <member-id>`。发布模式读取唯一执行卡中的相应计划，并额外核对：确认的 Domain/Module 是否全部落地并 reviewed；每个 Module 是否记录精确 requestedScope、selector 与 ready evidence；每个 Domain 是否完成源码 coverage；outcome 是否终结；四个 Domain Business 索引是否位于 canonical 路径；implemented Module 是否有至少一个 frontmatter `anchors.locations`；机器生成正文是否没有源码路径；每项图表决定是否记录 readerQuestion/mechanism 并按 visual id 落地或带理由豁免。

验证器不得要求固定标题、章节顺序、H3/分片数量、topic 齐全、页首导航、business 固定字节、额外 coverage receipt、方法级证据预算、全局图数量、中文正则、固定缩写替换表或专业术语全部翻译。普通 `clean` 只表示机械完整；publication `clean` 只表示执行卡字段、selector 语法/源码边界、执行状态和可机械检查的文件承诺一致；不读取 bundle 重放查询，也不认证卡片正文中的证据消费记录。两者都不替代正文真实性、充分性、可读性和专业性的人工语义回读。

## CAS 发布

`modus knowledge update` 只接受项目根相对的 `modus/knowledge/` 下 Markdown 路径。`documents` 和 `deletions` 不得混入根目录 `README.md`、`evidence.md`、源码或测试；需要同步这些普通项目文件时，按任务授权使用宿主编辑工具单独修改。路径或请求形状不合法时，CLI 在任何写入前拒绝整批请求（退出码 `2`）；这与合法请求执行中的逐文件 CAS 冲突不同。

通过 `modus knowledge update --input <更新请求.json>` 提交，临时 JSON 放在正式知识目录之外。输入字段如下；示例中的路径、完整正文和摘要都要替换为本轮真实值：

```json
{
  "documents": {"modus/knowledge/domain/example/references/rule.md": "修订后的完整 Markdown"},
  "expectedHashes": {"modus/knowledge/domain/example/references/rule.md": "读取原正文时记录的 SHA-256"},
  "deletions": [],
  "allowTeamStandard": false,
  "initializeTeamStandard": false
}
```

摘要按原正文的 UTF-8 编码计算，例如 `hashlib.sha256(before.encode("utf-8")).hexdigest()`；`before` 必须是本轮理解、修订所依据的完整读取结果。新建文件的预期摘要为 `null`，删除已有生成正文时在 `deletions` 列出路径并提供原摘要。普通同步保留 `allowTeamStandard: false`，不写人工约束或业务资料。退出码 `1` 表示存在逐文件冲突，已成功的写入不会回滚；检查报告的 `writes`、`unchanged`、`deleted` 和 `conflicts`，重读冲突正文后重新判断，不能只刷新摘要重试。

Team Standard 的两种写入方式互斥，默认均为 `false`：首次 init 的 K5 使用 `initializeTeamStandard: true`，仅填充缺失入口或与当前随包模板完全相同的入口种子；缺失专题还要求入口仍缺失或为精确种子。已有专题不享有种子覆盖例外。明确委托维护时才使用 `allowTeamStandard: true`，入口成稿后新增专题也属于维护。完整条件见[团队规范契约](framework/deliverables/team-standard.md#稳定入口与可选专题)。

二者必须为布尔值，同时启用在首个写入前拒绝整批请求。普通 reinit/update/sync 不自动选择这两种权限。首次填充遇到人工改动或旧版种子时保留实际内容，不能以“仍有种子注释”为由覆盖。先发布专题并确认成功，再单独更新入口导航；请求中的逐文件写入不构成事务，前一项冲突也不会自动阻止后续写入。

1. 完整读取目标并记录哈希；内容不变就跳写。
2. 新增先写目标并回读；更新保持原语义位置，不追加日期式 changelog。
3. 移动先写新落点、修复全部入站链接和导航，再按原读时哈希删除旧生成文件。
4. 人工 constraint/business 默认不改不删；明确授权时仍使用 CAS。
5. 冲突只重读受影响目标，禁止刷新哈希后盲目覆盖。
6. 发布后回读实际正文；只有唯一执行卡中的全部已确认创作目标均为 `reviewed`、每个 Module evidence 为 `ready`、每个 Domain coverage 为 `audited`、每个 Domain 有 `changed / unchanged` 终态，根概览完成，Team Standard 已按授权完成创作、保留核对或明确保持缺失的处置，且本轮实际运行的单仓 publication 或各已确认创作成员的 `--publication --member <member-id>` 核验为 `clean` 时，才进入清理。reinit 中规范缺失且未获补建授权时，在原卡正文说明缺失与影响，不伪称已创作、不生成悬空链接，也不因缺失阻止已授权工作的正常收尾。再核对卡片正文中本轮约定的整页/逐图验收均完成，没有待修问题或待验位置，才删除执行卡并只清理空目录；存在 `blocked` 或视觉待验项时保留卡片供恢复。普通 verify 的 `clean` 不得替代 publication，机械检查也不能清除正文中的验收缺口。执行卡不得提前删除；删除后发现正文仍需补写，不能从输出反向拼装一张最小执行卡获取 `clean`，而应如实报告收尾顺序错误并从完整权威状态恢复。

最终报告真实写入、删除、未更新原因、机械结果、实际回读与预览范围，以及仍存在的事实缺口和未验证项；不得把自查描述为独立读者验收，或把未运行的检查描述为通过。
