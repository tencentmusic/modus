# 增量知识维护

`modus-update-knowledge` 与 `modus-sync-knowledge` 共用本流程。入口决定范围和权限，本页负责从变化追到主定义、消费者与发布结果；证据、正文质量和 CAS 仍由共享细则定义。

## 范围与权限

| 入口 | 变化依据 | 结构与人工内容 |
| --- | --- | --- |
| update | 用户明确要纳入的当前源码、事实或材料 | 复用已有授权；真实新增、拆并、迁移或退役合并确认一次；人工内容仅在明确委托范围内维护 |
| sync | 当前代码任务实际产生且影响长期知识的 diff | 不接管已有脏改动；超出本轮授权的结构变化留给显式工作流；人工约束与业务资料默认保护 |

两者不构建或读取初始化 bundle，不运行全量 K1–K6，不创建或改写初始化执行卡。中断后先核对本轮目标、读时哈希、已写结果与待验项，再读取相关当前正文；不能以最后一次工具报错推断整批未写入。复用已充分的证据，不运行固定的无影响检查。

## 从变化到受影响正文

1. **确定主定义。** 读取相关完整正文、适用规范与当前源码/材料，记录原始哈希。使用[证据指南](evidence/index.md)及[场景闭合](evidence/scenario-closure.md)核对事实，把实现行为、目标要求、示例与推断分开。无新增事实或正文已准确时跳写；sync 无长期影响时静默结束。
2. **追踪实际消费者。** 从变化的接口、对象、规则、状态、资源或完成信号追到使用它的 Module、专题、Domain 路由及根概览。跨域交接双向核对提供方与消费者的字段映射、已提交事实、完成与恢复责任；只展开会改变这些结论的关联页，不能只改提供方，也不能借此全库重排。未变化的主定义和导航保持原位。
3. **核对工程约束。** 工程机制变化时联读 Team Standard 的适用范围、依据、例外与验证方式；业务规则仍留在所属领域。默认保持 `initializeTeamStandard: false` 和 `allowTeamStandard: false`。明确委托维护或补建规范才选择 `allowTeamStandard: true`，按[团队规范合同](framework/deliverables/team-standard.md)定向核查当前证据；不能因文件缺失、仍是种子或实现已改变而自动获得权限。未获维护授权的规范偏差说明位置和影响，不靠改政策消除差异。
4. **原位修订。** 按[生成框架](framework/index.md)与[编辑规则](framework/editorial.md)修订主定义、消费者和相关导航。校验、阈值、优先级或执行顺序变化时，重算已有正反例首先命中的分支，联读步骤、表格与图；可运行的关键例子用当前实现复核。按需参考[对照样稿](framework/examples.md)，不复制样稿事实、不追加日期式 changelog。
5. **处理已授权结构变化。** 按[Scope 建模](evidence/scope-modeling.md)复用稳定身份；只采用其中的身份与结构决策规则，不进入初始化取证或执行卡流程。先建立并回读新落点、修复入链和导航，再按原哈希退役旧生成文件。新增已确认 Domain 后，用 `modus knowledge seed-business --domain <slug> --json` 补齐缺失索引，保留已有人工材料。

## 验收与发布

按[发布合同](publication.md)完整回读所有受影响页面及关联上下文，用具体读者任务核对能否独立理解。变化的图表和版式实际预览，修复后重看；工具不可用时说明具体页面、未验项和影响。独立读者仅在已有委派授权和隔离上下文可用时增强验收，不以自查冒充。

使用读时哈希提交 CAS 写入，回读实际字节后对每个受影响 Domain 运行 `modus knowledge verify --domain <slug> --json`。涉及根概览、跨域迁移或共享导航时，运行普通 `modus knowledge verify --json` 检查共享链接；这是只读机械核验，不授权重写其他域。局部维护不使用要求初始化执行卡的 `--publication`。

请求被拒绝时先修正输入；逐文件冲突时保留已成功写入，查看 `conflicts` 与 `deferredDeletions`，只重读和重新判断受影响目标，不能刷新哈希后盲目覆盖。无变化不写；发生写入时报告实际变更、机械结果、回读/预览覆盖及剩余缺口。sync 的静默仅适用于无影响，不能掩盖冲突、部分成功或需要用户处理的规范偏差。
