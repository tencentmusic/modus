# 接口专题契约

API 表示项目对外承诺的调用面，不局限于 HTTP：Backend 包括 HTTP/RPC/GraphQL/消息入口，Frontend 包括路由/动作/组件契约，CLI 包括命令/参数/退出码，Library 包括 public exports，Worker/Data/IaC/Plugin 分别包括任务、作业、声明和宿主入口。

总览以契约族、调用者、用途、输入输出和完成语义导航。每个详情回答前提/权限、字段、独有分支、权威写入或交接、返回究竟表示受理还是完成、错误与恢复、兼容性、实现与关联知识。

## 总览与详情

先按调用目的或稳定契约族建立总览，而不是按源码文件罗列：

| 契约/入口 | 调用者与目的 | 关键输入 | 返回/产物 | 完成语义 | 详情 |
| --- | --- | --- | --- | --- | --- |
| 业务名称＋协议身份 | 谁为什么调用 | 决定行为的字段 | 响应、事件或资源 | 受理/同步完成/异步完成 | 本文锚点 |

随后以真实契约命名 H3。每个详情应说明：

- 协议身份、路由/命令/导出/任务名、调用者和适用/不适用场景；
- 鉴权、租户、状态和其他业务前提的实际检查顺序；
- 入参/出参字段的类型、业务含义、来源、缺省、约束和行为影响；
- 主流程、独有分支、权威写入、消息/下游交接和返回时点；
- 错误条件、异常映射、部分成功、幂等/重试和恢复责任；
- 兼容与演进约束、实现位置、关联 Object/Rule/State/Module 和验证入口。

字段表不能只复制 DTO 类型。至少解释会改变权限、路由、状态、金额、时间、分页、幂等或下游请求的字段，并区分未传、空值、零值和特殊枚举。嵌套对象的完整字典可以链接 Object，但当前接口的用途和差异仍应就地说明。

纳入范围的每个接口都应有完整字段说明或可定位的共享字典，不能只展开少数关键字段而遗漏其他请求/响应项。详情先说明调用方为何使用它，再按前提、参数、处理与返回、错误组织；在对应位置给出明确标注的请求/响应或调用示例，说明示例中的成功处于哪个业务阶段。失败案例覆盖该接口独有的条件差异，不重复粘贴一套通用错误段落。可参考[受理与完成的编辑样例](../examples.md#受理与完成)。

多级鉴权、参数分流、fallback 或读写策略用决策表/流程图；保存后发消息、多下游、返回后异步、回调或非原子远端副作用用时序图。简单同步查询只需精确表格和文字，不强制画图。

总览每一项都应有详情或明确的唯一主定义。只列几个“代表接口”、只写“参数见 DTO”“调用 Service 后返回”或把一个 Facade 文件视为一个契约，会掩盖同文件中不同方法的输入、完成和错误语义。

完成标准：所有正式公开入口都有归属、排除或真实缺口；同一契约的独有字段与完成语义没有被通用描述抹平。
