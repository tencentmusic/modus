# K3：证据闭环

围绕当前 Domain 的真实任务取证，让同一事实同时服务专题与模块。与 K4 按工作单元往返，不要求先把全库源码装进上下文。

## 输入与必读

- 输入：执行卡、本域目标与精确 Module selector、跨域交接、已读材料与缺口。
- 首次进入或上下文丢失时执行[上下文保存与恢复](../context-continuity.md)；先读卡，再取证、读相关正文、加载适用规范；切域或普通重试按该合同复用仍完整有效的内容。
- 读取[证据原则](../evidence/index.md)、[机器证据](../evidence/machine-packet.md)、[场景闭合](../evidence/scenario-closure.md)、对应构建单元的[语言适配器](../evidence/language-adapters/index.md)，以及[跨域协作](../cross-domain.md)。

## 执行

1. 每个 Module 用自身 candidate/capability/path/symbol 请求 `module-authoring` context，核对双摘要及 packet `requestedScope` 与实际请求逐轴相同，再核对原卡中的 Module ID → 请求范围映射。整域宽请求不能推进多个独立 Module；同场景不可分割的共享请求须符合机器合同并记录原因。
2. 归并精确源码位置，回读方法体、装配、配置、SQL、迁移、测试及用户材料。失败、空结果或 partial 时定向补证，记录 `source-fallback` 与原因；不得将签名、类名、文件首行或 `ready` 标签当作已读证据。
3. 逐场景闭合：角色与目标 → 触发/输入 → 前提/权限 → 判断顺序 → 编排/权威写入 → 返回/异步交接 → 最终可见结果 → 失败残留/恢复/验证。只描述实际存在的成功、失败、部分成功、取消、重试或恢复分支。
4. 规则判定需要时以本 Module 的精确范围请求 constraint-extraction，复用已取得的同源 signals；按[消费记录](../evidence/machine-packet.md#六阶段消费与可恢复记录)登记确认、反例/限制、未决或排除及正文落点。按[事实投影](../evidence/scenario-closure.md#从机器线索到正文主定义)分别消费入口、对象、效果、资源与关系；从声明、注册和实现建立逐接口、逐对象成员、逐规则和逐状态转换的清单，映射正文主定义。核对默认值、取值、单位、配置生效和上下游责任。按 K2 选择记录核验模块装配/调用和版本，标明选用、排除或待确认。公共工具、客户端、组件、转换器、线程池和配置门面记录准确入口、签名、空值、单位、异常、副作用、资源归属及代表使用者；找出不适用条件与危险旧写法，不能只抄类名。当前实现、业务要求、示意案例和待确认项明确区分；冲突记录来源、影响与未决原因，不能悄悄选一种描述。
5. 逐边核验图形候选、目标语言术语、案例输入与结果。跨域事实核对生产方和消费方，按共享协作合同更新原卡及受影响范围；不能仅沿本域代码推断对方完成或恢复保证。
6. 根作者按实际结果更新 Module evidence 和既有状态；未闭合条目保留位置与下一动作。机器材料或源码确实不适用时按范围合同记录原因，不能为提高完成率省略已确认范围。

## 产出与出口

同时给 K5 留下编码场景、复用契约、工具生效/团队偏好冲突和已核验公共机制的定义、实际使用者、适用范围、反例/旁路、强制检查与来源，在原卡中标明规则性质仍待提炼。无需重新扫描各专题，也不在本阶段提前写团队政策；局部业务规则随 K4 成稿。

当前单元有可复核事实与明确边界后进入 [K4 领域成稿](k4-domain.md)。事实不足继续 K3；范围变化回 K1。域级 `coverage-audit` 在 K4 验收时基于已确认源码范围执行，不以已生成知识路径作为 selector。
