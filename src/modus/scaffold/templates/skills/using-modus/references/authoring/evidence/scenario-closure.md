# 场景事实闭合

按真实任务调查一次，再把事实投影到不同正文。不得为 `api.md`、`object.md` 和 Module 分别重复扫描同一链路。

init/reinit 使用下述执行卡、机器 selector 和阶段规则；update/sync 只复用受影响场景的取证、条件核对和事实投影方法，按[增量维护流程](../incremental.md)在当前上下文处理，不创建工作记录文件、不进入初始化取证，也不要求全域接口/字段对账。已有正文未收录的入口或平台分支仍可能属于受影响场景，不能据此排除。

```text
触发 → 输入 → 前提与关键判定 → 编排 → 权威写入或产物
     → 返回或异步交接 → 最终可见结果 → 失败残留与恢复
```

## 事实分类

| 类型 | 正文表达 |
| --- | --- |
| 当前实现事实 | 直接说明当前行为，并给最小充分证据 |
| 用户或团队要求 | 明确写成目标要求，不伪装为已实现 |
| 已验证文档意图 | 指出声明来源和适用范围 |
| 基于证据的推断 | 标注“推断”、依据和不确定边界 |
| 真实不可得 | 写明已查范围、缺失内容和影响 |
| 尚未调查 | 不能进入终稿 |

“尚未调查”不能包装成“真实不可得”。静态可能路径不能写成必然运行轨迹；注释与实现冲突时同时说明当前行为和目标意图。

解释项目术语时，核对注释、类型/枚举定义、调用上下文与相关文档，按[通用表达规则](../framework/localization.md#术语解释行为表达与来源追溯)确定名称及适用范围。声明可以支撑命名含义，行为仍须回读实现、配置与测试；不得仅凭缩写拼写、方法名、布尔值或成功码推断用途和最终完成。未证实的含义保留原词，同名异义与材料冲突分别记录范围和差异，不擅自合并。

对正文要使用的状态、分类、开关与枚举，沿相关定义核对“类型/字段 → 成员 → 实际传输值 → 已定义中文名称”，包括构造参数绑定、注释、字典/国际化配置和显示转换；不能只读业务方法中的英文常量。机器包没有附中文释义时定向回源码或明确材料补齐，不把缺少投影当作没有定义。将确认的名称及适用范围记入已有场景记录，完整映射落到对象/状态主定义；按[中文含义应用规则](../framework/localization.md#已定义中文含义的应用)在正文、案例和图中复用，已获取的名称不能只停留在证据记录中。

## 从机器线索到正文主定义

先按[回包解释](machine-packet.md#回包解释)找到当前 intent 实际交付的记录。下表是取证与使用路线，不是要求每个项目出现所有信号；缺少某类信号不证明能力不存在。机器通常不交付完整字段字典、业务目的、全部守卫或运行配置值，作者仍从相关声明、方法体、配置和材料补齐。

| 已交付线索 | 定向补证的问题 | 正文主落点与用途 |
| --- | --- | --- |
| `sourceEntry`、入口信号的 `contract`、`route`、`signature` | 声明是否实际注册？谁能调用？参数如何校验/转换？响应如何包装？每个方法何时返回？ | API 的逐接口清单与详情；把所属入口用于 Module 场景起点 |
| `authoritativeObjects`、表/资源信号、写入效果、声明中的类型 | 谁实际读写？实体、请求、事件、响应分别有哪些继承/嵌套字段？默认/枚举/单位从何而来？ | Object 的完整成员字典、表示映射与变化案例；权威存储职责进入 Infrastructure |
| `transaction`、`lock`、`idempotency` 等效果信号 | 作用范围与先后顺序是什么？代理/装配是否生效？条件不满足时拒绝、跳过还是继续？ | Rule 的判定与例外；锁/事务资源边界进入 Infrastructure，接口重放条件回到 API |
| `state`、`terminalEffects`、`representativePaths` | 哪个只是步骤，哪个有持久写入？成功返回、发送、消费与最终可见结果是否分开？失败后留下什么？ | State 的转换表/图与完成条件；API 和 Module 保留各自操作的完成口径 |
| `sourceRelation`、`serviceRelation`、消息入口、topic/queue 信号 | 调用/装配是否成立？参数怎样映射？返回如何使用？谁确认和恢复？超时是否可能已经产生副作用？ | Downstream 的双向交接和时序；对象映射与 Module 中的协作步骤精确链接 |
| config/cache/table/topic/queue 等资源信号及相关路径句柄 | 配置从哪里加载、覆盖、默认、生效？资源何时创建/失效/释放？故障影响哪个业务步骤？ | Infrastructure 的资源、配置与恢复说明；需要改变结果的条件进入 Rule |
| K3 已核验机制、同源约束信号、共享配置与检查入口 | 使用者是否真正经过该机制？构建/CI 是否执行检查？哪些旁路或变体构成例外？ | K5 的项目约束、性质和适用范围；域/模块保留业务差异，K6 链接规范主定义 |
| coverage、ambiguity、remainder、needs-split、omitted 与未解析关系 | 会不会遗漏入口、分支、字段或另一责任方？哪些能在本地补证，哪些确实不可得？ | 原卡保留处置；会限制读者判断的真实边界在相关详情就地说明，不能转成“无此能力” |

同一行或同一方法可能同时提供锁、数据写入、发送等不同信号，按记录身份和实际含义分别核对；同源信号多次出现则复用，不因命中多次提高可信度。代表路径仅用于开始调查，继续沿该场景的失败出口、调用方和被调用方补齐条件，不能把一条代表路径直接翻译为整个模块。

当前单元的工作记录保存“来源 → 事实与条件 → 主定义 → 场景/图/案例使用处”。可以按完整场景合并记录，但要能识别哪些只是已取得线索、哪些已经回读成立、哪些已进入正文。已核验事实若暂未写入，检查点明确下一落点；不把 `recordId`、机器术语或整份工作记录搬进读者正文。

案例从这份已核验事实推演：选一组明确标注的示例输入，按真实判断顺序算出分支、写入后的值、返回值和最终完成信号；再改变一个关键条件，说明失败残留及可执行的下一动作。将该案例投影到各专题时各自解释所拥有的问题，Module 串起全过程。参考[跨页投影样例](../framework/examples.md#同一事实进入不同正文)，不能让六篇正文变成同一段流程的复制品。

## 闭合范围

关闭所有正式公开契约及其独有输入输出、影响结果的关键字段、核心对象、规则、状态与恢复、运行时协作、配置和资源边界。复杂图中的参与者、方向、状态、条件和完成信号逐边核验；仍可本地查证而未验证的边不能进入正式图。

在唯一执行卡已有场景记录中，把入口族展开为实际公开操作，把范围内对象展开为完整成员集合，关联各自主定义落点和剩余缺口。取证与正文使用同一清单，但清单来自声明、注册、序列化和实现，不能来自已经生成的文章。按[接口合同](../framework/deliverables/api.md#逐接口展开与对账)与[字段合同](../framework/deliverables/object.md#字段闭合)处理共享、继承、嵌套与动态边界；每个成员有基础定义，行为关键成员进一步追查分支。机器代表路径和 coverage 不代替这份事实对账。

将容易写反的条件在场景记录中表达成“输入条件 → 实际选值/分支 → 副作用 → 返回/完成”，包括否定布尔、兼容回退、短路、状态迁移和部分成功。对分支两侧分别找依据；注释、声明与实现不一致时保留差异。记录精确到仍待核对的接口、字段或条件，不能只写“对象待完善”。这些工作事实供压缩恢复和跨页核对复用，不复制进长期正文作为验收日志。

每个结论保留足以复核的仓库相对证据。源码路径和行号统一进入目标生成文档 frontmatter 的 `anchors.locations`；正文只保留有助于理解、修改和验证的业务名称、协议身份与限定符号，不写 `path#L` 或源码清单。根概览和 Domain 以稳定知识链接为主，确需直接追溯时也遵守同一 frontmatter 协议。得到足以回答当前问题的证据后停止，不为凑页数、条目数或“读完机器层”继续扫描。

进入一个 Module 时先消费只映射到该 Module 的精确 selector `module-authoring` context，再把 representative path 当作调查起点。Domain 级宽请求不能代替这一步。必须读取决定行为的方法体及其真实装配、调用方、配置、SQL/迁移和相关测试；文件名、类名、接口签名、注解或 packet signal 只能定位，不能单独证明场景。对每个公开入口关闭其独有字段、分支、权威写入、完成和恢复后，才把执行卡从 `pending` 更新为 `evidence-ready`。

调查时可以在唯一执行卡正文保留简短场景工作记录，但不要新建平行 receipt。每个场景至少记住以下可写事实，再一次性投影到专题和 Module：

| 事实问题 | 需要找到的证据 |
| --- | --- |
| 谁为何触发 | 公开入口、调用方、任务/事件注册或用户动作 |
| 输入怎样改变行为 | 字段校验、缺省/枚举、权限、分流和短路方法体 |
| 什么被权威写入 | 事务、SQL/迁移、状态存储、文件/产物或远端事实 |
| 返回意味着什么 | 响应、退出码、确认、回调、查询或最终可见信号 |
| 失败留下什么 | 异常映射、已提交副作用、重试/补偿选择和人工入口 |
| 改动怎样验证 | 对应测试、观测点、构建或真实检查命令 |

一次源码读取可以同时回答多个问题；不要为了不同文档重复扫描。反过来，一次读取只看到类声明或方法签名时也不能宣称场景闭合。尤其避免把文件首行、Facade 名称或测试类存在当作行为证据。

源码证据采用少量代表性锚点：优先保存术语定义、公开入口、关键判定、权威写入、完成/失败与恢复位置，并使用仓库相对路径和限定符号。支撑解释的项目文档使用已有 `anchors.paths` 记录代表性文件；准确源码位置使用 `anchors.locations`，不为文档虚构符号或行号。锚点只放 frontmatter，用于复核正文结论；不把每个方法或每一行复制到知识库，也不让正文退化为锚点的自然语言包装。
