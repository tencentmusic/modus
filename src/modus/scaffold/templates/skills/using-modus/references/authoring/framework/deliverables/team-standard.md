# 团队规范契约

Team Standard 是首次 init 从真实证据提炼的工程边界、复用导航和有条件的编码默认方案，随后默认转为人工所有。仅当状态为 `missing` 或 `framework-seed` 时初始化；`retained-content` 原样保护，`unavailable` 报告缺口。reinit/update/sync 不自动补建或刷新，除非用户明确委托。

内置模块的组织与最终产物分开：内置内容通过[组合合同](../../../../../modus-init/references/constraint-profiles/composition.md)渐进选择；目标项目保留稳定入口，按真实场景提炼，不机械拼接六维内容。

按项目机制自然组织，至少回答：构建与运行的架构边界；公开契约、数据/状态、配置、安全、资源和兼容在变化时必须保持什么；真实测试、lint、构建、codegen、CI、发布、迁移和回滚怎样执行。

## 推荐覆盖面

K5 消费 K1 的材料/权限与技术栈、K2 的主定义计划、K3 的原始机制证据和反例、K4 的最终使用场景。正文帮助定位事实，不能单独证明“必须”；规则依据回到声明、实现及生效检查。K6 只引用规范入口与理解系统必需的摘要，完整条目仍归本页所有。

首次填充通过 `modus knowledge update` 的 `initializeTeamStandard` 输入选择，使用读时哈希；缺失目标使用 `null`。写入时在文档锁内重新检查精确种子和 CAS，调查时的状态不是写入保证。后续维护使用独立的 `allowTeamStandard`，不能在初始化冲突后自动升级权限，见[CAS 发布](../../publication.md#cas-发布)。

项目约定须由仓库、工具配置、CI、测试或明确材料证明。通用建议可帮助实际编码，但须单独标明适用条件，不表述为项目已采用的政策。优先覆盖会直接影响编码的内容：

| 约束面 | 应回答的项目问题 |
| --- | --- |
| 编码默认写法 | 字符串/空值/比较、集合去重/分组/索引、对象转换、方法组织与复杂条件怎样写；格式、命名、注释与工具检查如何一致 |
| 复用与任务 | 默认使用哪些已核实工具、组件、客户端、基类、线程池、数据访问和配置门面；批量/异步的结果、超时、取消与资源怎样处理 |
| 命名与结构 | 包、模块、公开类型、配置、迁移和测试怎样命名；新能力放在哪里；哪些目录或层不能反向依赖 |
| 模块划分 | 业务能力、协议适配、编排、领域逻辑、数据访问和基础设施怎样分责；何时扩展现有模块，何时新建边界 |
| 注释与文档 | 哪些非显然约束、兼容原因、单位和副作用必须解释；哪些自明代码不需要重复注释；公开契约用什么文档形式 |
| 错误处理 | 错误怎样分类、包装、映射和传播；哪些可重试/可降级；何处记录上下文；怎样避免吞错、重复副作用和秘密泄漏 |
| 扩展与兼容 | 扩展点、注册/发现方式、默认实现、版本/迁移承诺和弃用路径；怎样新增能力而不修改无关分支 |
| 一致性 | 事务、锁、幂等、缓存/索引刷新、消息与远端副作用的边界；受理、提交和最终完成怎样区分 |
| 工程验证 | 格式化、lint、类型检查、测试、构建、codegen、迁移、发布和回滚的真实命令与适用范围 |

结构说明必须落到“依赖方向和修改责任”，不能只打印目录树；命名规范应附仓库中的正例和反例边界，不能把一次偶然命名泛化为政策。注释规范重点保护原因、单位、边界、危险副作用和兼容约束，不鼓励逐行复述代码。

错误处理需要串起“产生 → 分类/包装 → 边界映射 → 对外可见 → 观测与恢复”，并说明事务提交、消息发送或远端调用之后的错误会留下什么。可扩展性需要指出稳定接口、组合/注册机制、兼容面和验证责任，而不是笼统要求“低耦合”。

每条规则说明性质、适用范围、要求、依据、合法例外和验证。源码事实不自动成为政策，归纳约定要检查反例，明确约束要有人工声明或可验证强制机制。不得虚构 owner、SLA、审批、安全扫描、生产超时或兼容承诺。

推荐用简短场景导航作为入口，按当前任务选择，简单条目不套长表。复杂场景展开默认方案、复用入口、示例前提、关键边界、替代方案和验证：

| 条目要素 | 正文应回答 |
| --- | --- |
| 场景与性质 | 什么任务会用到？这是已采用约定、明确要求，还是通用建议？ |
| 适用范围 | 哪些路径、平台和版本适用？哪些不适用？ |
| 默认方案 | 复用哪个准确入口？参数、错误、副作用与资源由谁负责？ |
| 依据与示例 | 哪些声明或实现支撑规则？示例需要哪些真实依赖和前提？ |
| 例外与验证 | 何时换方案？如何检查成功、失败和兼容边界？ |

如果同一主题在仓库中存在多种做法，应说明各自适用边界或记录为待确认项，不要强行归并成一条“统一规范”。通用建议与已采用约定分开；未知 API、版本不兼容和不安全历史写法不能成为默认示例。示例注明对应规则性质、真实依赖/版本和前提，不把“示例”当权威等级。

## 稳定入口与可选专题

小项目只维护 `constraint/team-standard.md`。内容密度确实妨碍选择时，可增加 `constraint/team-standard/<topic>.md` 一级专题，入口保留范围、性质说明及场景导航。已有更深专题仍属于同一人工命名空间，不因深度改变保护或检索身份。一个规则只有一个主定义；专题使用稳定 item 锚点，每条开头保留性质、状态、范围与版本，示例/失败子节不得脱离前提。专题不链接安装目录内的指南作为项目事实来源。

入口和专题均为人工所有，检索 authority 为 `document-declaration`；性质仍按条目判定。普通 reinit/update/sync 不补建或重写，安装指南升级也不改变这些正文。两种显式权限互斥，且都保留 CAS 检查：

| 目标当前状态 | 首次填充 `initializeTeamStandard` | 明确维护 `allowTeamStandard` |
| --- | --- | --- |
| 入口缺失或为精确随包种子 | 可填充 | 可按授权写入 |
| 入口已有保留内容 | 拒绝改写 | 可按读时哈希修订 |
| 专题缺失，入口仍缺失或为精确种子 | 可创建 | 可按授权创建 |
| 专题缺失，入口已成稿 | 拒绝创建 | 可按授权创建 |
| 专题已存在，包括内容恰好等于入口种子 | 拒绝改写 | 可按读时哈希修订 |

相同正文可幂等重试，不获得额外维护权。删除 API 不退役人工入口或专题。

发布分两步：先写专题并回读，确认所需专题全部成功后，再提交入口链接。首次专题写入先取得入口锁，再取得专题锁，并复查入口状态，防止等待期间入口已交还人工。该顺序只协调单文件发布，不提供多文件事务；部分失败保留已成功正文，按实际结果回读恢复，不能升级权限覆盖。

完成标准：用与调优样稿分开的代表性编码任务，从导航实际找到默认能力和前提，产出可检查的代码/修改草稿，核对 API、格式/工具、失败/并发/资源、无关依赖和抽象。覆盖本项目实际环境组合，包含版本或规则冲突负例；记录实际运行和未运行项。链接/schema 检查不能替代编码效果。初版完成后交还人工维护。
