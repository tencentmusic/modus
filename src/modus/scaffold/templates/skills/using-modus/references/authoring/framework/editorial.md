# 正文编辑与阅读排版

本合同负责把已经闭合的事实组织成可独立阅读的知识。事实边界由[场景闭合](../evidence/scenario-closure.md)确定，术语由[本地化](localization.md)定义，图形选型由[图文表达](visual-expression.md)定义。目录、已有标题层级、元数据和人工内容沿用[布局合同](layout.md)；编辑不授予结构迁移或扩大修改范围的权限。

## 写前确定阅读任务

对当前目标页面先确定读者、需要解决的问题、贯穿案例、必讲分支及事实主落点，再安排正文、步骤、表格和图。init/reinit 复用唯一执行卡正文中的主定义/图形计划和场景工作记录；局部更新复用当前任务的修改计划，不另建卡或 receipt。

问题来自已确认范围和证据，不能只从已经写出的正文反推。例如接口页应回答调用条件和返回代表的阶段；对象页应让读者预测字段变化的影响；模块页应让读者从目标走到可观察结果。计划保持简短，不把每个问题强制转换成一个标题。

| 需要表达的内容 | 优先形式 | 配套解释 |
| --- | --- | --- |
| 背景、原因、边界、因果关系 | 连贯段落 | 谁在什么条件下得到什么结果 |
| 必须依次执行的操作 | 编号步骤 | 前提、分支、每步的可观察结果 |
| 同类对象的字段或条件对照 | 表格 | 影响结果的例外和字段间关系 |
| 调用、状态、归属、数据变化 | 最小有用图形 | 图前说明问题，图后解释关键分支 |
| 一个任务的端到端过程 | 贯穿案例 | 输入、判断、变化、完成及失败处置 |

## 章节与段落的阅读顺序

章节开头先给本节的业务要点，再按理解依赖展开。先介绍对象或条件，再使用其名称解释行为；先说明正常过程，再在发生分叉的位置解释异常。正常流程中的关键限制不能只留到文末注意事项。

一段围绕一个问题，使用能说明主体、动作、条件和结果的句子。多个事实存在因果关系时用正文连接；只有真正并列的项目才用列表。避免整页项目符号让读者自行拼过程，也避免把无关事实连成大段。段长和列表密度是复查线索，不是字数或行数门槛。

标题保持当前层级，用实际场景或条目区分内容。已有清楚的标题不因样稿措辞不同而重命名。页首概览用于定位，后续详情负责解释；不要用第二张概览表代替正文。

长页的导航链接到实际接口、对象或场景详情，不能只跳到另一层概览。相邻层级表达包含关系，避免跳级和用整句加粗冒充标题；列表、表格、代码块与段落之间留空行。加粗突出结论或关键条件，不把整段变成视觉重点。协议值用行内代码，连续多行的调用和返回用带语言的代码块；同一示例的说明、调用和结果放在一起。

排版检查要能指向具体问题：一段同时解释多个分支就按判断拆段；一格容纳整条流程就移成正文；一页只有表和列表就补上因果主线；详情过长就按业务分组并补导航。保持正常阅读宽度下从上到下可读，不靠横向滚动、缩小字号或反复跳页完成一个基本任务。

## 详实来自可使用的信息

默认交付可用于开发和排障的详实手册，为范围内的接口、字段、规则、状态、协作和场景留足篇幅。先完整展开，再组织层次，不以“简洁”为由省掉已确认的业务细节，也不把后续领域压成摘要。每个重要事实应解释适用条件、行为影响或验证方法；新增文字应让读者多完成一个判断、操作或定位任务。不要用重复背景、泛化中间件常识或同义总结代替业务内容。

补充内容时优先回答“为什么调用、怎样输入、在哪里分支、改变了什么、凭什么确认完成、出错后怎样继续”。对会改变结果的规则，给出满足与不满足条件时的差异；对字段，解释实际取值和组合怎样改变行为；对任务，写出操作前后可观察结果。接口清单、字段组摘要和一句“支持重试”都不能充当这些详情。字数随真实范围和复杂度增长，不设统一篇幅上限，也不靠固定最低字数验收。

用明确标注的示例数据串联一个场景：谁带着什么目标发起、输入怎样影响判断、对象或状态怎样变化、何时算完成、异常时保留什么。不同路径的完成或恢复方式不同，就分别展开；一个正常案例不能代表所有失败分支。

案例需要能核对的输入与结果：正常案例展示主线，边界或失败案例展示本场景容易误判的条件、残留和下一动作。只写“例如创建一条记录”仍是概述。相同事实在专题给完整定义，在场景给适用解释，避免通过重复整张字典增加篇幅。

例子遵循已经核验的实现或明确业务要求。未实现的取消、重试、降级和补偿不能因模板提问而补造；尚未调查与确实不可得分开记录。业务背景若缺少明确材料，只说明可证实的用途，不从方法名猜测业务意图。

## 表格保留精度，正文承担解释

字段、规则、配置和状态表保留可查阅的精确信息。列标题短而具体，同一列回答同一种问题；单元格尽量不承担完整流程或多段论述。长解释移到紧邻正文，以字段名或规则名精确关联。

推荐合同中的列表示应覆盖的信息，不要求挤在一张表内。宽表按语义拆为基础字典、约束/读写、表示映射，或资源职责、配置生效、故障恢复等组；重复稳定的字段或资源标识以便对照，不能拆表后丢失必填、默认、单位和例外。

长表先按业务意义分组，再决定是否需要已有合同允许的分片。不得只因行数超阈值创建新文件或改变目录。表前说明查什么，表后解释关键条件和例外；请求响应示例使用代码块，不塞进宽单元格。

## 图与正文共同解释过程

每张图紧邻相关说明。图前交代它回答的问题及阅读起点；图后解释关键条件、责任交接、完成信号和图中省略的细节，不逐节点复述图中文字。标签、状态名和接口身份与正文一致。

节点放短业务名称，完整条件在相邻表格或正文中展开。复杂机制拆为总览和局部分支，说明图之间的接续点；不要把流程、时序、状态和全部字段塞入一张图，也不要靠缩小字体容纳所有信息。图的事实和实际预览要求见[图文表达](visual-expression.md)。

## 独立阅读与唯一主定义

专题保存完整契约，模块解释契约怎样参与本次任务。模块保留理解本场景必需的条件、对象作用和完成口径，再精确链接专题；不能只写“详见链接”让读者跳页补全过程，也不能复制整份字段字典和完整机制图。

共享事实变化时核对其主定义、场景摘要和图中的使用处。摘要可以省略非当前场景的细节，不能省略会改变当前判断的条件。源码坐标仍只进入现有 frontmatter；正文必须能在隐藏元数据后读懂。

## 编辑回读

成稿后完整读当前目标页，检查段落是否连贯、步骤是否可执行、表格是否易查、图是否解释了独立问题。使用[成对样例](examples.md)校准相似缺陷，不复制其业务事实和标题。编辑完成后回查接口值、条件、否定词、状态与图中文字，防止润色改变语义。

段落组织与实际显示分别验收。Markdown 作者能决定信息分块，阅读器决定字号、行距、可用宽度和图形缩放。按[发布合同](../publication.md)记录实际阅读环境及未验证项；代码围栏存在、图形语法检查或源码回读均不等于实际页面可读。
