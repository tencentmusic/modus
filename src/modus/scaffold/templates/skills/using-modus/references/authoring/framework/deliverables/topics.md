# 六专题总则

六专题是跨场景事实的唯一主定义面，不是按 Module 平铺的摘要：

| 入口 | 主定义对象 | 详细合同 |
| --- | --- | --- |
| `api.md` | 公开契约及其完成语义 | [API](api.md) |
| `object.md` | 权威对象、字段和表示映射 | [Object](object.md) |
| `rule.md` | 判定、优先级、例外与不变量 | [Rule](rule.md) |
| `state_machine.md` | 状态、端到端链路、失败与恢复 | [State Machine](state-machine.md) |
| `downstream.md` | 上游、下游、宿主与交接责任 | [Collaboration](collaboration.md) |
| `infrastructure.md` | 资源、配置、生命周期与运行边界 | [Infrastructure](infrastructure.md) |

每个 H3 以真实契约、对象、规则、状态系统、协作方或资源命名。总览链接到唯一详情，不能停在第二个总览。一个详情可以服务多个 Module，但必须写清差异；其他位置精确链接，不复制完整定义。

专题正文面向读者解释事实，不陈列源码证据。需要追溯时把少量代表性源码位置写入当前文件 frontmatter 的 `anchors.locations`；正文保留业务名称、协议身份、限定符号、修改职责与验证方式，但不出现仓库源码路径、行号或“证据”段落。移除 frontmatter 后，每个详情仍应独立回答行为、边界、失败与修改问题。

确无独立事实时，可以用简短“已核验边界”说明调查范围及事实所在位置。不得生成空表、空详情或用 Module 列表填充专题。

## 共同写作节奏

每个专题先给面向定位的总览表，再按真实事实逐项展开。总览不是正文替代品：每一行应链接到本文件详情或明确的唯一主定义。详情至少把“是什么”推进到“何时发生、由谁负责、怎样改变结果、失败会留下什么、从哪里修改和验证”。

详情先说明当前条目的用途与关键结论，再用段落、窄表、步骤或案例展开；总览与字段表过宽时按语义拆分，完整保留条件和标识。推荐表头表示需要解释的信息，不要求在一张表中容纳所有列。排版方法见[编辑合同](../editorial.md)，不要靠重复概述或复制 Module 正文增加篇幅。

专题之间按责任去重：

- API 定义调用承诺和完成语义，不重复对象完整字段字典；
- Object 定义事实源、字段和表示映射，不重复所有接口流程；
- Rule 定义改变结果的判定、优先级和例外，不把职责介绍写成规则；
- State Machine 定义状态、推进者、终态和恢复，不把普通类调用冒充状态；
- Downstream 定义交接责任和失败边界，不只罗列依赖名称；
- Infrastructure 定义影响结果的资源与运行条件，不写通用中间件教程。

复杂内容使用“总览表＋解释性图＋逐项正文”：表格负责精确字段、条件或责任映射，图负责方向、顺序、状态或关系，正文负责原因、边界、例外和恢复。只有五行的“本专题包括……代表入口是……”通常意味着仍停留在目录级摘要，应返回源码继续展开。

API/Object 分片只在至少两个稳定语义组且单文件已影响导航时使用。根文件保持全域入口；分片只允许一层，按调用目的、所有权、生命周期或表示族分组。新增优先进现有组，更新不因长度洗牌，移动先修新落点/根索引/入链，再 CAS 删除旧详情。
