# using-modus

为当前任务补充项目知识和实现证据。先明确要理解、修改或判断什么，再选择足以支持该目标的正文与源码；已有证据充分时直接使用。仅在任务依赖当前项目事实时加载，不能因为会话位于已安装 Modus 的目录就自动介入。若任务实际进入实现修改，则由本 Skill 持有知识留存检查点，直到最终交付前完成语义影响判断。

> **核心不变量**：按任务渐进取证，结论回到当前源码；正文知识提高定位效率，但不扩大用户授权；修改任务在最终答复前完成一次静默的知识影响判断。

## 激活边界

需要理解、修改、评审或排查当前项目实现，或需要基于项目事实创作文档时，按需使用本 Skill。查询股票、一般问答、翻译用户给出的文字、仅整理用户已提供材料等不依赖当前项目证据的任务，不检查 `.modus/` 或 `modus/`，不检索项目知识，也不触发知识同步。

## 知识留存检查点

1. 本轮实际开始修改项目实现、公开契约、运行配置或源码锚点时，在当前 Agent 上下文中保留一个待决的知识留存检查点。它不是文件、命令、扫描、报告、审批或持久状态，不改变原任务节奏。
2. 完成实现与验证后、输出最终答复前，以当前任务目标、实际编辑与差异为起点判断影响，包含本轮新增、删除、移动和已提交的修改；不能只看最后的工作区是否干净。复用本轮已读证据，必要时定向核对差异，不做固定全仓扫描。不接管原有脏改动或其他作者的并发修改；归属不清时先核对，不能把它当作无影响。
3. 本轮变化涉及长期职责、场景、接口、对象、规则、状态、依赖、资源或源码锚点时，加载 `modus-sync-knowledge`。影响尚不明确、出现未归属的新入口或找不到知识落点时，也交给它定向调查；已有正文未提及、候选为空或机械检查返回 `noop` 都不能证明无影响。是否需要写入由调查后的事实决定。
4. 只读理解、诊断、评审、纯知识编辑、无关文档修改及项目外任务不因此授权同步写入。格式或测试等调整只有确认不改变应维护的长期事实时才跳过，不能仅按文件类别排除。已证实无影响时静默结束，不加载同步 Skill、不运行固定检查、不输出 noop。

待判断的影响、已确认范围与未完成项只随当前上下文或已有会话摘要交接，不另建记录文件。恢复时核对当前源码与正文；上下文不足以还原本轮范围时如实说明缺口，不能宣称已经同步。

## 渐进增强

1. 复用用户请求、对话、材料、显式路径和已经核实的证据。已知知识路径、源码路径、接口或符号时直接深入；范围不明时，按[共享检索与降级说明](references/router-details.md)从根 `architecture-overview.md` 选路，再沿 Domain `SKILL.md` 、Module 手册和专题知识渐进读取，最后回到当前源码核验。
2. 按任务应用 `modus/knowledge/constraint/`、相关域 `references/rule.md` 和模块规则，必要时读[约束使用说明](references/constraint-usage.md)。将适用要求落实到方案、实现和验证，区分当前事实、明确规范、归纳约定、通用建议和待确认事项。编码前沿 Team Standard 场景导航取得适用范围、准确复用入口、默认写法、示例前提与例外，核验版本/平台后应用；不要只读风险禁令。
3. 自动消费默认且只读本轮源码、用户材料和 canonical `modus/knowledge/`。本流程禁止读取 `modus/.cache/init-analysis/`，也不导入、构建或刷新初始化分析；调用链、影响面和拓扑判断从正文导航到当前源码核验。
4. 阅读片段时保留祖先标题、所属接口/对象/场景、前提和例外；被截断时沿准确的条目范围续读。新人理解优先 Module 因果主线，改规则联读相关判定与契约/对象，排障联读失败现象、状态与依赖；不是固定文件清单。得到足以完成目标的证据后回到原任务，已有证据不重复检索。

`modus context resolve "问题" --scope project-read` 是便利接口；变更调查可以用 `--purpose change`。续查时重新传入具体问题、purpose 和显式 path，每轮读取当前正文与源码。CLI、知识、缓存和安装记录均不是前提。普通消费不初始化、不构图、不补模板、不改写知识。

用户明确请求创建或维护知识时，分别使用 `modus-init`、`modus-reinit` 或 `modus-update-knowledge`；材料用于当前任务不自动代表持久保存授权。显式要求更新 Modus 软件包时读[包更新说明](references/framework-update.md)。

## Git 提交信息

生成或润色提交信息时，以本次拟提交的实际差异为依据，并遵循以下约定：

1. 优先遵循用户要求和项目明确的提交规范；没有明确规范时参考相关模块的历史约定；仍无约定时采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)。语言、长度等要求随项目约定，不额外设置统一限制。
2. 采用 Conventional Commits 时，标题格式为 `<type>[(<scope>)][!]: <summary>`，方括号表示可选部分。按实际行为选择 type：新增能力用 `feat`，修复错误用 `fix`，不改变行为的重构用 `refactor`，仅修改说明文档用 `docs`；其他类型沿用项目约定。Skill 模板可能定义产品行为，不能仅凭 Markdown 扩展名归为 `docs`。
3. 摘要写清改动对象和结果，避免仅写“优化”“完善”“调整”。简单变更可以只有标题；复杂变更在空行后的正文说明问题或动机、修改后的行为、相关验证与兼容性影响，不罗列文件清单代替解释。验证只记录实际执行的检查及结果，未执行或未通过的检查如实说明。
4. 采用 Conventional Commits 且存在破坏兼容性的变更时，用 `!` 或 `BREAKING CHANGE:` 标记，并说明影响与迁移方式；关联事项和其他页脚按项目约定填写。

这些约定只规范提交信息，不授予 Git 提交、推送或改写历史的权限；相关操作沿用当前任务已有授权。
