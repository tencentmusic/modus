# 并发、异步与批量任务

适用存在并发执行或异步交接的场景，不要求把串行逻辑改成并发。以下为通用建议；语言入口负责 Future、coroutine、Promise、goroutine 等具体语义。证据从执行器/scope/调度装配、提交者、任务体、结果消费者和关闭者形成闭环。

先找项目批接口和专用执行能力，核实负载隔离、准入上限、队列/拒绝、上下文、异常及生命周期。共享池不等于适合所有任务；不能复制固定线程/队列数。CPU、阻塞 I/O、事件循环和后台可靠任务分开判断，无必要时保持串行。

默认流程：校验批次与结果契约 → 有界准入 → 显式传入业务身份/截止时间 → 局部产生结果 → 汇总并报告失败 → 清理。避免一次提交无限任务、并发写普通可变容器、同池嵌套同步等待。容量由实际预算与负载确定。

| 边界 | 默认行为与取舍 |
| --- | --- |
| 提交拒绝 | 提交处处理；未得到 Future/Promise 的失败不能交给完成回调；已接收任务仍须结算 |
| 任务失败 | 消费每个结果或定义明确的失败聚合；不能 log 后返回空成功；部分成功按已有结果协议 |
| 超时 | 使用总截止时间或同一预算，逐项等待不重置完整超时；区分排队、执行与下游预算 |
| 取消 | 向真实支持取消的调用传播；停止等待不代表任务/外部写入停止；晚到结果须被处理或隔离 |
| 上下文 | 核实传播和恢复；可变线程上下文不假定深拷贝；线程/任务切换不自动传播事务 |
| 清理/停机 | 调用方不关闭共享资源；停止准入、结算已收任务并在真实恢复机制下退出，不能宣称强制终止 |

如何换方案：没有适用共享能力时，先解释现有能力的限制，再按任务新增最小机制；可靠后台任务有持久化/重试需求时不能用临时内存 Future 代替。检查空批、重复项、饱和拒绝、一个任务失败、慢任务、取消、中断、部分成功和停机；成功路径或静态检查不能证明这些边界。
