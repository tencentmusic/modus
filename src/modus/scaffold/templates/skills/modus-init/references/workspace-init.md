# 工作区外层导览与成员补齐

本流程只在当前根存在可读 `.modus/config.yaml` 且明确声明 `kind: workspace` 时生效。workspace 根只拥有跨仓知识导览，不拥有成员业务 Domain；成员配置、源码、知识与 Git index 都属于各成员仓。

## 1. 只读盘点

在 workspace 根首次进入时执行一次且只执行一次 `modus status --json`，使用返回的 `workspace.counts` 与 `workspace.members`；后续阶段复用该结果，不重复执行。不可用时从已明确配置的成员与当前文件只读盘点，不以安装或修复工具为前提。该盘点必须全程只读，并按每个成员路径的第一层非 Git 父目录展示：父目录只作为章节名，不是成员、仓库、系统或能力实体；根下直属成员统一放在“根目录”章节。

每个成员展示路径、安装态、知识内容态、可读证据入口和缺口原因，并在开头汇总总数、已安装/未安装数，以及 `available / partial / missing / unavailable` 数量：

- `available`：可观察到结构完整的正式 Domain 知识。
- `partial`：已有正式知识内容，但可观察到结构缺项；这不是内容质量评分。
- `missing`：没有正式知识。空目录、cache、单独根概览、constraint 或 business 内容均不算正式知识。
- `unavailable`：成员或知识路径不安全、不可读或文档不可读。

这些名称只用于本轮命令输出和决策，不落盘、不写进知识正文、不成为发布门禁、CURRENT 状态或收据。盘点失败的成员继续以 `unavailable` 展示，不阻断其他成员。

## 2. 一次合并范围确认

先从请求和只读盘点判断范围。用户已明确选择外层导览、指定补齐成员或给出完整 Scope 时采用既有授权；不能仅因成员知识不完整自动初始化或重建成员。

存在 missing/partial 成员且用户未说明是否补齐时，在同一轮 Scope 展示中提供“仅建设外层导览（推荐）”与“补齐所列成员后建设外层导览”的范围选择。先完成足以支持选择的只读调查，将涉及成员、可复用或拟新增 Domain/Module、真正结构变化与生成文件删除范围汇总到一张执行卡；不另设逐成员审批。补齐与结构决定合并一次语义确认，已明确的成员范围不反复询问。

全部成员已有知识且请求明确刷新外层导览时直接执行，不新增“是否刷新”审批。unavailable 成员报告实际原因并继续其他成员，不猜测路径或扩大写入授权。

## 3. 仅建设外层导览

所有成员保持只读，不在成员根运行安装、写知识或 init-analysis 构建，不修改成员 Git index。读取成员当前源码、配置、契约和已有正文。

只更新外层导览，不在 workspace 根创建 Domain/Module，不把跨仓描述冒充成员业务身份。默认不写 handbook/references/business；用户明确指定的人工维护或本轮已确认结构变化下最小知识链接修复，按共享生命周期的授权与 CAS 执行。

## 4. 补齐已确认成员

确认后按所列成员独立执行，复用单仓的固定正文树、六专题、Module 九类必答语义与 surface 画像、因果内容和写入合同：missing 成员需要安装时在其根执行 modus init，再完成首次正文；partial 成员复用可恢复稳定 Scope，全量复核约定范围。available 与 unavailable 成员除非另在用户明确范围内，否则保持只读。

独立成员可并行调查和写作，同一文件一个作者；每个已确认需要初始化的成员作为独立单仓同步构建一次 init-analysis，只消费自己的本轮 bundle，成员间不得混读。成员流程不再次发起 Scope/策略确认；构建失败就回到该成员当前源码，不重试。某成员失败仅报告实际受影响范围，继续其他成员与外层导览；Provider 失败不能当作成员全局无事实。

合并 scope-confirmation.md 记录已确认范围、实际完成状态与剩余项，不创建新状态体系或分仓回执。已确认退役/合并先修新落点与入链/导航，再 CAS 精准删除成员生成文件，保留人工文件路径和语义；历史交给各成员 Git。仅在当前授权涉及的成员中写入，跨到只读成员的链接缺口在结果说明，不擅自修复。

成员的每个 Domain 生成或压缩后恢复前，都按[逐域加载与恢复](../../using-modus/references/authoring/evidence/scope-modeling.md#逐域加载与恢复)执行；从这张合并执行卡定位对应成员与本域范围、Module 归属、selector 和进度，再加载该成员证据、相关已有正文和写作规范。委托时传入合并卡实际路径与成员身份，不在成员根另建卡，也不沿用其他成员的摘要或 selector。

## 5. 外层导览发布

保留并刷新以下既有结构，不新增目录或持久状态标记：

```text
modus/knowledge/handbook/
├── SKILL.md
└── references/
    ├── business/**                         # 人工所有权，默认保留
    └── generated/
        ├── member-map.md
        ├── system-map.md
        ├── capability-map.md
        ├── service-map.md
        ├── feature-map.md
        ├── contract-map.md
        ├── object-map.md
        ├── infrastructure-map.md
        ├── delivery-map.md
        ├── fact-status.md
        └── members/<repositoryId>.md
```

十张地图和成员卡按第一层非 Git 父目录分章节。系统、服务、契约、能力、功能、对象和基础设施条目直接附成员源码、配置、契约或已有知识的 Markdown 链接；链接必须指向真实文件，必要时带可复核符号或行号。证据不足时用自然语言说明“尚未在可读源码中确认”等不确定性，不添加 `available`、`partial`、`CURRENT` 或其他证据状态标签。

可读成员调查完成后统一汇总十张地图与成员卡，先写叶子地图再更新 SKILL 导航；不可访问或未完成成员说明实际边界，不把它当作其他成员或外层导览的发布门槛。已有文件先读取并携带首次读取哈希，通过公共安全写入会话执行 CAS；并发冲突只影响冲突文件，必须报告且不得覆盖。地图刷新不要求所有成员完整，也不把成员失败升级为硬门槛。最后回读全部实际写入文件，核对父目录分组、成员稳定 ID、重复仓名区分、真实链接、十张地图齐全，以及人工 business 区仅发生已授权编辑或最小链接修复，所有成员非目标文件未被修改。

用实际跨仓理解、规则变更或排障问题回读路径、角色、契约交接和失败边界；不新增机械语义门禁。全范围完成后以本轮身份及读时哈希清理确认卡，只移除空目录；仍有可恢复成员时保留剩余项。外层正文结果和成员机器构建状态分别报告。
